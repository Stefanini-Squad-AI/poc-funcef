Visão full-stack FUNCEF

A arquitetura alvo FUNCEF é um sistema distribuído em três camadas de produto — frontend, backend e dados — unificado por contratos, identidade corporativa e padrões de entrega. Este capítulo dá o mapa mental antes de mergulhar nos detalhes de cada família.

Fluxo de confiança (Full BA)

No cenário padrão (Full Better Auth / Entra), o browser não chama a API de microsserviço diretamente com credenciais expostas. O fluxo canônico é:

Usuário → Next.js (login Entra via @funcef-componentes/auth)
       → BFF same-origin (/api/bff) resolve Bearer server-side
       → API .NET (FUNCEF.Autenticacao valida token)
       → PDP GAP (autorização por ação, se [FuncefAuthorize])
       → Oracle / Redis / Key Vault
Por quê BFF? Mantém tokens e políticas de sessão no servidor Next; reduz superfície CORS; alinha com o template web-template onde features chamam api<T> em @/core/api, nunca um client HTTP ad hoc no browser.

Backend — quatro camadas

Cada microsserviço segue Clean Architecture. Dependências apontam para dentro:

API (Controllers, Program.cs)
  → Application (Commands, Queries, Handlers, Services, Validators)
    → Domain (Entidades)
  → Infrastructure (DbContext, DI, integrações FUNCEF.*)

Detalhe: BE-02 Clean Architecture.

Frontend — quatro camadas

app/ (rotas Next.js, orquestradores)
  → features/ (domínio: hooks, api, components, validators)
    → core/ (auth, config, api client, providers)
      → shared/ (UI genérica, utils)

Regra rígida: features não importam de outras features — código compartilhado sobe para shared/ ou core/. Detalhe: FE-01.

Componentização FUNCEF.*

Dez bibliotecas NuGet coordenadas (pin [3.0.0,4.0.0), FUNCEF.Abstractions em 3.1.0). Contratos compartilhados (ICacheStore, ISecretReader, paginação) vivem em Abstractions; implementações ficam nas libs especializadas. Mapa completo: Componentes FUNCEF.*.

Dados e entrega

  • Modelagem: PadraoBD v2.2 — prefixo TB_, PK surrogate NUMBER IDENTITY, boolean NUMBER(1) CHECK IN (0,1) (ADR-017).
  • Versionamento: Liquibase em repositório DB-as-Code — feature/fix → dev → hom → main via PR.
  • Spec: comportamento definido em UCs/contratos (SDD); código cita a spec. Ver Processos de entrega.
