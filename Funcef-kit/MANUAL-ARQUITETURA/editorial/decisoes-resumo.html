Decisões arquiteturais (ADRs)

ADRs registram contexto, decisão, alternativas rejeitadas e consequências. São imutáveis — mudanças geram novo ADR que supersede o anterior. Abaixo, os ADRs mais relevantes para quem implementa na stack FUNCEF (resumo; detalhe na Doutrina).

Decisões recentes de configuração (2026)

SecretRef canônico — Toda referência a segredo usa subseção <Coisa>FromKeyVault: { Enabled, SecretName }. Sintaxes antigas (*KeyName, UseKeyVaultForX) foram removidas das libs; chaves legadas são ignoradas (fail silencioso).
Redis — Seção de configuração = NoSql:RedisCache (não NoSql:Redis). Refresh token usa Auth:RefreshToken:StorageType = "Redis" após AddRedisCache.
Audience Entra v2 — Com requestedAccessTokenVersion=2, o aud do access token é o ClientId GUID puro; config deve usar o GUID (não api:// salvo cenário v1).

Como usar ADRs no dia a dia

  1. Antes de propor exceção (“vamos usar AutoMapper”, “vamos pular Service Layer”), verifique se há ADR ou princípio que proíbe.
  2. Exceções aprovadas ficam registradas em Excecoes-Aprovadas.md — não são defaults.
  3. Mudança de padrão → novo ADR + atualização da Doutrina e agentes em dual-write.
