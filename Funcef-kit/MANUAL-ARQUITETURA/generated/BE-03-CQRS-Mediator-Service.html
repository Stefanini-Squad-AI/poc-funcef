BE-03 — CQRS, Mediator e Service Layer

3.1 Modelo conceitual

ConceitoImplementação
**Command**`ICommand` (void) ou `ICommand` — intenção de mudança de estado
**Query**`IQuery` — intenção de leitura
**Handler**`ICommandHandler` / `ICommandHandler` / `IQueryHandler` — executa o caso de uso
**Notification**`INotification` (marcador) + `INotificationHandler` — evento de domínio in-process, com **0..N** handlers
**Mediator**`IMediator.Send(command)` despacha Command · `IMediator.Receive(query)` despacha Query · `IMediator.Publish(notification)` despacha Notification
**Pipeline**`IPipelineBehavior` — middleware do Mediator; `ValidationBehavior` é o behavior canônico
**Validator**`AbstractValidator` do FluentValidation — só Commands têm
**Service**`I{Entidade}Service` — regras de negócio + acesso a dados (via `IRepository`)

Todas as interfaces vêm do componente FUNCEF.Essenciais (FuncefEssenciais.Application.Commands, FuncefEssenciais.Application.Queries, FuncefEssenciais.Application).

3.2 Send para Commands, Receive para Queries, Publish para Notifications

O Mediator FUNCEF (IMediator : ISender, IReceiver, IPublisher) distingue explicitamente as operações no contrato:

MétodoAceitaHandlersSignificado
`Task Send(ICommand)`Command que retorna1Mudança de estado
`Task Send(ICommand)`Command void1Mudança de estado sem retorno
`Task Receive(IQuery)`Query1Leitura pura
`Task Publish(INotification)`Notification**0..N**Evento de domínio in-process (publish/subscribe)

Ler o nome do método no código já diz a intenção. Decisão registrada em Decisoes-Arquiteturais ADR-003.

3.2.1 Notifications (Publish) — eventos de domínio in-process

Use Publish para desacoplar efeitos colaterais da lógica principal (auditoria, e-mail, invalidação de cache). Diferente de Command (exatamente 1 handler), uma INotification pode ter 0 ou mais INotificationHandler.

// Evento (marcador INotification)
public record ClienteCriadoNotification(long ClienteId, string Nome) : INotification;

// Handler — auto-registrado por AddMediatorWithDefaults; pode haver vários
public class AuditarCriacaoCliente : INotificationHandler<ClienteCriadoNotification>
{
    public Task Handle(ClienteCriadoNotification n, CancellationToken ct) => /* ... */;
}

// Publicação — tipicamente no Handler de um Command, após persistir
await _mediator.Publish(new ClienteCriadoNotification(cliente.Id, cliente.Nome), ct);
```

Aviso **Semântica de execução (FUNCEF.Essenciais v3.0.0)**

Os handlers de uma notificação rodam **sequencialmente** e **in-process** (mesmo processo). Falhas de handlers individuais são **agregadas** em `AggregateException` ao final — um handler de auditoria/telemetria com bug **não impede** os demais (mudança v3.0.0). `OperationCanceledException` por cancelamento é propagada imediatamente. **Não** use `Publish` para integração entre microserviços — para isso use mensageria (Azure Service Bus via `FUNCEF.Armazenamentos`); `Publish` é para eventos **dentro** do mesmo serviço.

3.3 Estrutura de pastas (CQRS)

Convenção rígida:

Commands/
└── {Entidade}/
    └── {Acao}/
        ├── {Acao}{Entidade}Command.cs    # ICommand<TResponse>
        ├── {Acao}{Entidade}Handler.cs    # ICommandHandler<TCommand,TResponse>
        └── {Acao}{Entidade}Validator.cs  # AbstractValidator<TCommand>

Queries/
└── {Entidade}/
    └── {Detalhe}/
        ├── Get{Entidade}{Detalhe}Query.cs    # IQuery<TResponse>
        └── Get{Entidade}{Detalhe}Handler.cs  # IQueryHandler<TQuery,TResponse>
```

Exemplos de ações típicas: `Create`, `Update`, `UpdateStatus`, `Delete`, `CreateCom{X}Ef`, `CreateCom{X}Dapper`.

Exemplos de detalhes típicos: `GetById`, `GetPaged`, `GetBy{Filtro}`.

3.4 Anatomia de um Command

using FuncefEssenciais.Application.Commands;
using {Servico}.Application.DTOs.{Entidade}Dto.Request;
using {Servico}.Application.DTOs.{Entidade}Dto.Response;

namespace {Servico}.Application.Commands.{Entidade}.Create;

public class Create{Entidade}Command : ICommand<{Entidade}Response>
{
    public {Entidade}Request Request { get; set; } = new();
}
```

Padrões:

  • O Command é uma **classe pública** com propriedades públicas (não record). É instanciada pelo controller via `new Create{Entidade}Command { Request = request }`.
  • O payload de entrada típico vai dentro de uma propriedade `Request` que carrega o DTO de Request — isso simplifica os Validators (`x => x.Request.Campo`) e reduz duplicação entre Command e DTO.
  • `Update{Entidade}Command` adicionam um `Id` no **nível do Command** (não no DTO), porque o ID vem da rota.

3.5 Anatomia de um Validator

using FluentValidation;
using FuncefEssenciais.Core.Validation.FluentValidation;

namespace {Servico}.Application.Commands.{Entidade}.Create;

public class Create{Entidade}Validator : AbstractValidator<Create{Entidade}Command>
{
    public Create{Entidade}Validator()
    {
        this.RuleForRequiredText(x => x.Request.Nome, "nome", 100);
        this.RuleForOptionalEmail(x => x.Request.Email, maxLength: 150);
    }
}
```

Padrões:

  • Validator valida **o Command**, não o DTO. Permite validar combinações entre `Id` (vindo da rota) e propriedades do Request num único lugar.
  • Usar **métodos de conveniência do FUNCEF** (`RuleForRequiredText`, `RuleForOptionalEmail`, `RuleForRequiredId`, `RuleForPositiveDecimal`, `RuleForRequiredAllowedValues`, `RuleForPagination`, `RuleForSortField`, `RuleForSortDirection`) — padronizam mensagens em PT-BR e limites do projeto.
  • Detalhes em [BE-06-Validacao-Excecoes](../seguranca/BE-06-Validacao-Excecoes.md).

3.6 Anatomia de um Command Handler

using FuncefEssenciais.Application.Commands;
using FuncefORM.Contracts;
using FuncefORM.Mapping.Extensions;
using {Servico}.Application.DTOs.{Entidade}Dto.Response;
using {Servico}.Application.Services;

namespace {Servico}.Application.Commands.{Entidade}.Create;

public class Create{Entidade}Handler : ICommandHandler<Create{Entidade}Command, {Entidade}Response>
{
    private readonly I{Entidade}Service _service;
    private readonly IUnitOfWork _unitOfWork;

    public Create{Entidade}Handler(I{Entidade}Service service, IUnitOfWork unitOfWork)
    {
        _service = service;
        _unitOfWork = unitOfWork;
    }

    public async Task<{Entidade}Response> Handle(Create{Entidade}Command command, CancellationToken cancellationToken)
    {
        var entity = await _service.CreateAsync(command.Request, cancellationToken);
        await _unitOfWork.SaveChangesAsync(cancellationToken);
        return entity.MapTo<Domain.Entities.{Entidade}, {Entidade}Response>();
    }
}
```

Padrões:

  • **Sem `try/catch`.** Exceções tipadas (`NotFoundException`, `ConflictException`, …) sobem e são tratadas pelo `GlobalExceptionMiddleware`. Exceção: transações multi-passo com `Begin/Commit/Rollback` (§3.13).
  • O Handler **não chama o repositório diretamente** — sempre via Service.
  • O Handler **sempre chama `SaveChangesAsync()`** quando faz mudança de estado. O Service usa `_repository.AddAsync(entity)` mas não salva — quem decide quando persistir é o Handler.
  • `MapTo(…)` é a extensão do `FuncefORM.Mapping`; o DTO precisa de `[MapFrom("Prop")]` em cada propriedade que deve ser populada.

3.7 Anatomia de uma Query

using FuncefEssenciais.Application.Queries;
using {Servico}.Application.DTOs.{Entidade}Dto.Response;

namespace {Servico}.Application.Queries.{Entidade}.GetById;

public class Get{Entidade}ByIdQuery : IQuery<{Entidade}Response>
{
    public long Id { get; set; }
    public bool Incluir{Navegacao} { get; set; }   // quando aplicável
}
```
public class Get{Entidade}ByIdHandler : IQueryHandler<Get{Entidade}ByIdQuery, {Entidade}Response>
{
    private readonly I{Entidade}Service _service;
    public Get{Entidade}ByIdHandler(I{Entidade}Service service) => _service = service;

    public async Task<{Entidade}Response> Handle(Get{Entidade}ByIdQuery query, CancellationToken ct)
    {
        var entity = query.Incluir{Navegacao}
            ? await _service.GetByIdWithAutoIncludesAsync(query.Id, ct)
            : await _service.GetByIdAsync(query.Id, ct);

        if (entity is null)
            throw NotFoundException.ForResource("{Entidade}", query.Id);

        return entity.MapTo<Domain.Entities.{Entidade}, {Entidade}Response>();
    }
}
```

Padrões:

  • Queries **não injetam `IUnitOfWork`** — não fazem commit.
  • A decisão entre `GetByIdAsync` (sem includes) e `GetByIdWithAutoIncludesAsync` (com navegações marcadas com `[AutoInclude]`) fica no Handler/Query, não no Service.
  • Quando o recurso não existe, **o Handler de Query lança `NotFoundException`** — não devolve `null`.

3.8 Query paginada com filtro

Padrão de listagem com paginação, busca e ordenação:

public async Task<PaginatedResult<{Entidade}Resume>> Handle(
    Get{Entidade}PagedQuery query, CancellationToken ct)
{
    var sortDirection = query.DirecaoOrdenacao?.ToLowerInvariant() == "desc"
        ? SortDirection.Descending
        : SortDirection.Ascending;

    var pagedRequest = PagedRequest.Create(
        query.Pagina, query.TamanhoPagina,
        query.OrdenarPor ?? "Nome", sortDirection);

    Expression<Func<{Entidade}, bool>>? predicate = null;
    if (!string.IsNullOrEmpty(query.TermoBusca))
    {
        var termo = query.TermoBusca.ToLowerInvariant();
        predicate = e => e.Nome.ToLower().Contains(termo);
    }

    var pagedResult = await _service.GetPagedAsync(pagedRequest, predicate, ct);
    var dtos = pagedResult.Items.MapToList<{Entidade}, {Entidade}Resume>();

    return new PaginatedResult<{Entidade}Resume>
    {
        Items = dtos, Page = pagedResult.Page, PageSize = pagedResult.PageSize,
        TotalItems = pagedResult.TotalItems, TotalPages = pagedResult.TotalPages
    };
}
```

Tipos chave (`PagedRequest`/`SortDirection` de `Funcef.Abstractions.Pagination` — ver [CMP-08-Abstractions](../componentes/CMP-08-Abstractions.md); `PaginatedResult` de `FuncefORM.Data`):

TipoPapel
`PagedRequest`Encapsula `Pagina`, `TamanhoPagina`, `OrdenarPor`, `SortDirection`
`PaginatedResult`Resposta com `Items`, `Page`, `PageSize`, `TotalItems`, `TotalPages`
`SortDirection``Ascending` ou `Descending`
`MapToList`Mapeia uma `IEnumerable` para `List`

3.9 Pipeline `ValidationBehavior`

sequenceDiagram
    autonumber
    participant Med as IMediator
    participant Beh as ValidationBehavior
    participant Vdr as Validator(s)
    participant Hnd as Handler

    Med->>Beh: invoke(request)
    Beh->>Vdr: ValidateAsync(request)
    alt failures.Count > 0
        Vdr-->>Beh: ValidationResult com erros
        Beh-->>Med: throw ValidationException
    else
        Vdr-->>Beh: ok
        Beh->>Hnd: Handle(request)
        Hnd-->>Beh: response
        Beh-->>Med: response
    end
```

O behavior é registrado automaticamente por `AddMediatorWithDefaults(assembly)`. O `GlobalExceptionMiddleware` mapeia `ValidationException` para HTTP 400.

**Importante:** O behavior **só roda para Commands** (Validators são `AbstractValidator`). Para validar uma Query, fazer dentro do Handler.

3.10 Service — anatomia

public interface I{Entidade}Service
{
    Task<{Entidade}> CreateAsync({Entidade}Request request, CancellationToken ct = default);
    Task<{Entidade}> UpdateAsync(long id, {Entidade}Request request, CancellationToken ct = default);
    Task ValidateAndDeleteAsync(long id, CancellationToken ct = default);
    Task<{Entidade}?> GetByIdAsync(long id, CancellationToken ct = default);
    Task<{Entidade}?> GetByIdWithAutoIncludesAsync(long id, CancellationToken ct = default);
    Task<PaginatedResult<{Entidade}>> GetPagedAsync(
        PagedRequest request, Expression<Func<{Entidade}, bool>>? predicate = null,
        CancellationToken ct = default);
}
```
public class {Entidade}Service : I{Entidade}Service
{
    private readonly IRepository<{Entidade}> _repository;

    public {Entidade}Service(IRepository<{Entidade}> repository) => _repository = repository;

    public virtual async Task<{Entidade}> CreateAsync({Entidade}Request request, CancellationToken ct = default)
    {
        if (await _repository.ExistsAsync(e => e.CampoUnico == request.CampoUnico, cancellationToken: ct))
            throw new ConflictException("{Entidade}", "Já existe um registro com este {campo}");

        var entity = request.MapTo<{Entidade}Request, {Entidade}>(e =>
        {
            // Id NÃO é setado: PK IDENTITY gerada pelo banco no insert.
            e.DataCriacao = DateTime.UtcNow;
        });

        await _repository.AddAsync(entity, ct);
        return entity;
    }

    public virtual async Task<{Entidade}> UpdateAsync(long id, {Entidade}Request request, CancellationToken ct = default)
    {
        var entity = await _repository.GetByIdAsync(id, cancellationToken: ct)
            ?? throw NotFoundException.ForResource("{Entidade}", id);

        // ... aplica mudanças
        await _repository.UpdateAsync(entity, ct);
        return entity;
    }

    public virtual async Task ValidateAndDeleteAsync(long id, CancellationToken ct = default)
    {
        var entity = await _repository.GetByIdAsync(id, cancellationToken: ct)
            ?? throw NotFoundException.ForResource("{Entidade}", id);

        // Validações de integridade (ex.: tem dependentes?)
        await _repository.DeleteAsync(entity, ct);
    }

    public virtual Task<{Entidade}?> GetByIdAsync(long id, CancellationToken ct = default)
        => _repository.GetByIdAsync(id, cancellationToken: ct);

    public virtual Task<{Entidade}?> GetByIdWithAutoIncludesAsync(long id, CancellationToken ct = default)
        => _repository.GetByIdWithAutoIncludesAsync(id, cancellationToken: ct);

    public virtual Task<PaginatedResult<{Entidade}>> GetPagedAsync(
        PagedRequest request, Expression<Func<{Entidade}, bool>>? predicate = null,
        CancellationToken ct = default)
        => _repository.GetPagedAsync(request, predicate, cancellationToken: ct);
}
```

Padrões observáveis:

PadrãoPor quê
Métodos `virtual`Permite mock/override em testes e extensão por herança
Service **nunca** chama `SaveChangesAsync()`Quem decide quando persistir é o Handler — possibilita transações multi-Service
Validações de domínio antes da escritaFalha rápido com exceção tipada — sem corromper estado
`GetByIdAsync` retorna `null` para "não encontrado" no ServiceQuem traduz para HTTP 404 é o Handler (`?? throw NotFoundException.ForResource`) — exceto em UPDATE/DELETE onde o próprio Service já lança

3.11 Controller — anatomia

[Route("[controller]")]
[ApiController]
public class {Entidades}Controller : BaseController
{
    private readonly IMediator _mediator;

    public {Entidades}Controller(ITelemetry telemetry, IMediator mediator) : base(telemetry)
        => _mediator = mediator;

    [HttpPost]
    [FuncefAuthorize]
    [ProducesResponseType(typeof({Entidade}Response), StatusCodes.Status201Created)]
    [ProducesResponseType(StatusCodes.Status400BadRequest)]
    [ProducesResponseType(StatusCodes.Status409Conflict)]
    public async Task<IActionResult> Create(
        [FromBody] {Entidade}Request request, CancellationToken ct = default)
    {
        var result = await _mediator.Send(
            new Create{Entidade}Command { Request = request }, ct);
        return ApiCreated(result);
    }

    [HttpGet("{id:long}")]
    [FuncefAuthorize]
    public async Task<IActionResult> Get(long id, CancellationToken ct = default)
    {
        var result = await _mediator.Receive(new Get{Entidade}ByIdQuery { Id = id }, ct);
        return ApiOk(result);
    }

    [HttpDelete("{id:long}")]
    [FuncefAuthorize]
    public async Task<IActionResult> Delete(long id, CancellationToken ct = default)
    {
        await _mediator.Send(new Delete{Entidade}Command { Id = id }, ct);
        return ApiNoContent();
    }
}
```

Helpers de `BaseController` retornam `ObjectResult`s padronizados:

MétodoHTTPUso
`ApiOk(result)`200Leitura ou update bem-sucedido
`ApiCreated(result)`201Recurso criado
`ApiNoContent()`204Operação sem corpo (delete típico)

3.12 Registro automático no DI

`{Servico}.Application/Extensions/ServiceCollectionExtensions.cs`:

public static IServiceCollection AddApplicationServices(this IServiceCollection services)
{
    services.AddMediatorWithDefaults(typeof(ServiceCollectionExtensions).Assembly);

    services.AddScoped<I{Entidade1}Service, {Entidade1}Service>();
    services.AddScoped<I{Entidade2}Service, {Entidade2}Service>();
    // ... outros services

    return services;
}
```

`AddMediatorWithDefaults(assembly)` (do `FuncefEssenciais.Application.Extensions`) usa Scrutor para varrer o assembly e registrar:

Tipo registradoComo é encontrado
`IMediator`Singleton interno do FuncefEssenciais
`ICommandHandler<,>` e `ICommandHandler<>`Scrutor scan da assembly
`IQueryHandler<,>`Scrutor scan
`AbstractValidator<>` (FluentValidation)Scrutor scan
`IPipelineBehavior<,>` (incluindo `ValidationBehavior`)Defaults do FuncefEssenciais

**Conclusão:** **só Services precisam de `AddScoped` manual**. Handlers e Validators são automáticos.

3.13 Transações multi-passo no Handler

Quando o caso de uso envolve mais de uma operação que precisa ser **atômica**, o Handler controla a transação:

public async Task<{Resultado}Response> Handle({Comando}Command command, CancellationToken ct)
{
    await _unitOfWork.BeginAsync(ct);
    try
    {
        var entityA = await _serviceA.CreateAsync(command.RequestA, ct);
        await _unitOfWork.SaveChangesAsync(ct);

        var entityB = await _serviceB.CreateAsync(command.RequestB, ct);
        await _unitOfWork.SaveChangesAsync(ct);

        await _unitOfWork.CommitAsync(ct);
        return new {Resultado}Response { /* ... */ };
    }
    catch
    {
        await SafeRollbackAsync(ct);
        throw;
    }
}

private async Task SafeRollbackAsync(CancellationToken ct)
{
    try
    {
        await _unitOfWork.RollbackAsync(ct);
        _telemetry.LogWarning("Rollback executado com sucesso");
    }
    catch (Exception rollbackEx)
    {
        _telemetry.LogError("Erro ao executar rollback", rollbackEx);
    }
}
```

Detalhes (incluindo variante com Dapper) em [BE-04-Persistencia-Transacoes](../persistencia/BE-04-Persistencia-Transacoes.md) §4.7.

3.14 Mapa Command/Query → Handler → Service (padrão)

Command/QueryHandlerService usado
`Create{Entidade}Command``Create{Entidade}Handler``I{Entidade}Service.CreateAsync`
`Update{Entidade}Command``Update{Entidade}Handler``I{Entidade}Service.UpdateAsync`
`Delete{Entidade}Command``Delete{Entidade}Handler``I{Entidade}Service.ValidateAndDeleteAsync`
`Create{Entidade}Com{X}EfCommand``Create{Entidade}Com{X}EfHandler``I{Entidade}Service.CreateAsync` + `I{X}Service.CreateAsync` (com `IUnitOfWork.BeginAsync/CommitAsync`)
`Create{Entidade}Com{X}DapperCommand``Create{Entidade}Com{X}DapperHandler``…CreateWithDapperAsync` (vide [BE-04-Persistencia-Transacoes](../persistencia/BE-04-Persistencia-Transacoes.md))
`Get{Entidade}ByIdQuery``Get{Entidade}ByIdHandler``I{Entidade}Service.GetByIdAsync` ou `GetByIdWithAutoIncludesAsync`
`Get{Entidade}PagedQuery``Get{Entidade}PagedHandler``I{Entidade}Service.GetPagedAsync`

3.15 Quando NÃO criar um Service

Para queries muito simples (1-2 linhas de delegação ao repositório), o Handler **pode** chamar `IRepository` diretamente — mas o padrão dominante é Handler → Service. Manter o Service como camada estável ajuda em refactors e cobertura de testes. **Justificar** ao optar pelo atalho.

3.16 Padrão canônico: `IMediator` + `ICommand`/`IQuery` (vs `IUseCase` do projeto de referência)

Importante **Qual é o padrão (decisão 2026-05-26)**

O padrão **canônico** FUNCEF é o deste capítulo: despacho via **`IMediator`** (`Send` para Commands, `Receive` para Queries, `Publish` para Notifications), com `ICommand`/`IQuery` + `Handler` + `Service`, e respostas padronizadas no Controller via `BaseController` (`ApiOk`/`ApiCreated`).

O projeto de referência `api-nexus-cadastro` adota hoje uma variante (`IUseCase` + `UseCaseResponse` + `ProcessUseCaseResponse`). **Essa variante é uma divergência conhecida, não o padrão.** Ao escrever código novo, siga BE-03 (`IMediator`/`ICommand`). O alinhamento do projeto de referência ao padrão é tratado pela governança de BackEnd — não adote a variante por imitação.
