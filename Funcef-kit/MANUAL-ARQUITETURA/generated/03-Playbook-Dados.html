03 — Playbook Dados

Nota **Objetivo**

Entregar schema Oracle alinhado ao PadraoBD e à persistência BE (`FUNCEF.ORM`), via DB-as-Code (Liquibase).

[!CAUTION]

**Sem segredos**

Não documente connection strings, usuários/senhas Oracle, TNS de produção ou nomes internos de hosts. Acesso DEV/Hml vem do kickoff.

1. Princípios

  1. **Forward-only:** objetos legados existentes não são renomeados por iniciativa da fábrica; migração de legado é decisão de governança.
  2. **Objetos novos/alterados** seguem PadraoBD vigente.
  3. **DDL/DML de ambiente compartilhado** via Liquibase + PR — não scripts soltos em Hml/Prd.
  4. **PROD:** aprovação DBA.

2. Convenções canônicas (resumo)

TemaPadrão
Tabela`TB_` + **plural** UPPERCASE (`TB_TAREFAS`)
ColunaUPPER_SNAKE por extenso (`DATA_CRIACAO`, `TITULO`)
PK`{ENTIDADE}_ID` · `NUMBER` · `IDENTITY` · surrogate `long` no .NET
Boolean`FLAG_ NUMBER(1) NOT NULL` + `CHECK IN (0,1)` — **não** `BOOLEAN`
Texto`VARCHAR2(n)`
Data`DATE` (ou padrão do PadraoBD vigente para o caso)
SchemaUPPERCASE — nome `` do serviço (kickoff)

Alinhar 1:1 com atributos `[Table]` / `[Column]` da entidade EF (playbook Backend).

3. Exemplo didático — `TB_TAREFAS`

-- Ilustrativo — entregar como changeset Liquibase no repo DB-as-Code do projeto
CREATE TABLE <SCHEMA>.TB_TAREFAS (
  TAREFA_ID      NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  TITULO         VARCHAR2(200) NOT NULL,
  FLAG_CONCLUIDO NUMBER(1) DEFAULT 0 NOT NULL,
  DATA_CRIACAO   DATE DEFAULT SYSDATE NOT NULL,
  CONSTRAINT CK_TB_TAREFAS_FLAG_CONCLUIDO CHECK (FLAG_CONCLUIDO IN (0, 1))
);

COMMENT ON TABLE <SCHEMA>.TB_TAREFAS IS 'Tarefas didáticas do onboarding';
COMMENT ON COLUMN <SCHEMA>.TB_TAREFAS.TAREFA_ID IS 'Identificador surrogate';
COMMENT ON COLUMN <SCHEMA>.TB_TAREFAS.FLAG_CONCLUIDO IS '0=não; 1=sim';
```

Mapeamento EF (conceito):

ColunaPropriedade C#
`TAREFA_ID``long Id`
`TITULO``string Titulo`
`FLAG_CONCLUIDO``bool Concluido`
`DATA_CRIACAO``DateTime DataCriacao`
```

4.1 Checklist de changeset

  • [ ] Objeto novo/alterado conforme PadraoBD
  • [ ] PK IDENTITY + nome `{ENTIDADE}_ID`
  • [ ] `FLAG_*` com CHECK 0/1
  • [ ] COMMENTs em tabela/colunas relevantes
  • [ ] Idempotência / preconditions conforme padrão do repo
  • [ ] Sem dados sensíveis (CPF real, segredos) em seeds de exemplo
  • [ ] Validado em DEV antes de promover

5. Ambientes (visão)

AmbienteUso típico
DevelopmentIteração da fábrica; auto-migrate do template só se o kickoff autorizar
HomologationComportamento ~prod; mudanças via Liquibase
ProductionDBA; sem atalho

Connection strings e usuários: **kickoff / Key Vault** — nunca neste pacote.

6. Anti-padrões

  • Aplicar DDL manual em Hml/Prd
  • Usar `BOOLEAN` ou `CHAR(1) 'S'/'N'` em objeto **novo** (legado `S`/`N` permanece forward-only)
  • PK `GUID` / coluna `ID` genérica sem ADR
  • Duplicar tabela “espelho” só para contornar naming
  • Commitar dump com dados reais de participantes

7. Checklist — primeira tabela

  • [ ] Modelo lógico acordado com o BE
  • [ ] Changeset no repo DB-as-Code
  • [ ] Entidade EF alinhada
  • [ ] Smoke: insert/select via API em DEV
  • [ ] Sem secrets no PR
