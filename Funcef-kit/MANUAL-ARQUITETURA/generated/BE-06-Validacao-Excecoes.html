BE-06 — Validação e Tratamento de Exceções

6.1 Princípios

PrincípioComo aplica
**Validação acontece no pipeline, não no controller**`ValidationBehavior` roda antes do Handler; controller nunca tem `if (!request.IsValid)`
**Validators validam o Command** (não o DTO)`AbstractValidator<{Acao}{Entidade}Command>` referencia `x => x.Request.Campo`
**Apenas Commands têm Validators**Queries são validadas no próprio Handler quando necessário
**Erros viram exceções tipadas**`NotFoundException`, `BusinessException`, `ValidationException`, `ConflictException` (todas de `FUNCEF.Essenciais`; `ConflictException` herda `BusinessException` e mapeia 409)
**Exceções viram HTTP via middleware global**`UseGlobalExceptionHandler` mapeia tipos → status codes
**Nunca `try/catch` defensivo dentro do Handler**Exceção sobe; o pipeline + middleware decidem (única exceção: `Rollback` em transação multi-passo)

Decisão registrada em Decisoes-Arquiteturais ADR-004 e ADR-005.

6.2 Stack de validação

graph LR
    Req["HTTP Request"] --> Bind["Model Binding<br/>(ASP.NET)"]
    Bind --> Filter["FluentValidation<br/>Filter (global)"]
    Filter --> Ctrl["Controller"]
    Ctrl --> Send["IMediator.Send"]
    Send --> Beh["ValidationBehavior<br/>(pipeline)"]
    Beh --> Val["Validator(s)<br/>do Command"]
    Val -->|"ok"| Hnd["Handler"]
    Val -->|"falhas"| Ex["ValidationException"]
    Ex --> Mid["GlobalExceptionMiddleware"]
    Mid --> Resp400["HTTP 400"]
```

Camadas de validação:

  1. Model binding (ASP.NET) — falha com 400 se o JSON não bindar (tipo errado).
  2. FluentValidation filter global (AddFluentValidationFilterGlobally) — caso o controller receba um DTO com Validator registrado.
  3. ValidationBehavior do Mediator — onde realmente a validação de Commands acontece, porque o Validator é do Command e o Command é construído pelo controller.

6.3 Validator — padrão

using FluentValidation;
using FuncefEssenciais.Core.Validation.FluentValidation;

namespace {Servico}.Application.Commands.{Entidade}.Create;

public class Create{Entidade}Validator : AbstractValidator<Create{Entidade}Command>
{
    public Create{Entidade}Validator()
    {
        this.RuleForRequiredText(x => x.Request.Nome, "nome", 100);
        this.RuleForOptionalEmail(x => x.Request.Email, maxLength: 150);
    }
}
```

6.4 Métodos de conveniência do FUNCEF.Essenciais

Helpers ficam em FuncefEssenciais.Core.Validation.FluentValidation:

MétodoSignificadoErro típico
`RuleForRequiredText(x => x.Nome, "nome", 100)`Texto obrigatório com tamanho máximo`"O campo 'nome' é obrigatório."` / `"… até 100 caracteres."`
`RuleForOptionalText(x => x.Desc, "descrição", 500)`Texto opcional com tamanho máximoApenas se vier preenchido e exceder
`RuleForOptionalEmail(x => x.Email, maxLength: 150)`Email opcional, formato válido`"O e-mail informado é inválido."`
`RuleForRequiredId(x => x.Id, "id")`Guid não vazio (não `Guid.Empty`)`"O campo 'id' é obrigatório."`
`RuleForPositiveDecimal(x => x.Valor)`Decimal > 0`"O valor deve ser maior que zero."`
`RuleForRequiredAllowedValues(x => x.Status, valoresPermitidos, "status")`Valor em lista permitida (enum-like)`"O 'status' deve ser um dos: A, B, C."`
`RuleForPagination(x => x.Pagina, x => x.TamanhoPagina)`Página >= 1 e tamanho > 0 / <= limite`"A 'página' deve ser maior ou igual a 1."`
`RuleForSortField(x => x.OrdenarPor, new[] { "Nome", "DataCriacao" })`Campo de ordenação em allowlist`"O campo de ordenação deve ser um dos: Nome, DataCriacao."`
`RuleForSortDirection(x => x.DirecaoOrdenacao)``"asc"` ou `"desc"` (case-insensitive)`"A direção da ordenação deve ser 'asc' ou 'desc'."`

Vantagem: mensagens em português padronizadas em todos os microserviços FUNCEF, sem cada dev escrever a sua.

6.5 Quando criar regras customizadas

Quando os helpers não cobrem, usar a sintaxe nativa do FluentValidation:

public class Update{Entidade}StatusValidator : AbstractValidator<Update{Entidade}StatusCommand>
{
    private static readonly string[] StatusValidos =
        new[] { "Pendente", "Aprovada", "Cancelada", "Entregue" };

    public Update{Entidade}StatusValidator()
    {
        this.RuleForRequiredId(x => x.Id, "id");
        this.RuleForRequiredAllowedValues(x => x.Request.Status, StatusValidos, "status");

        // Regra customizada: 'Observacoes' obrigatória se status = Cancelada
        RuleFor(x => x.Request.Observacoes)
            .NotEmpty().WithMessage("A observação é obrigatória ao cancelar.")
            .When(x => string.Equals(x.Request.Status, "Cancelada", StringComparison.OrdinalIgnoreCase));
    }
}
```

6.6 Validators são registrados automaticamente

AddMediatorWithDefaults(assembly) (chamado em AddApplicationServices()) escaneia a assembly e registra qualquer AbstractValidator<>. Não há registro manual.

Para criar um Validator novo basta colocar a classe na pasta Commands/{Entidade}/{Acao}/{Acao}{Entidade}Validator.cs — ele será descoberto.

6.7 Pipeline ValidationBehavior — comportamento

CasoComportamento
Command sem Validator registradoPipeline passa direto ao Handler
Command com 1 ValidatorExecuta; se `IsValid = false`, lança `ValidationException` (do `FuncefEssenciais.Exceptions`) com a lista de erros
Command com múltiplos ValidatorsTodos executam; erros agregados em um único `ValidationException`
QueryValidators de Query **não são executados** pelo behavior (só `AbstractValidator`)

6.8 Tipos de exceção e mapeamento HTTP

Exceções da camada FuncefEssenciais.Exceptions:

ExceçãoHTTPUso típico
`ValidationException`**400 Bad Request**Falha do `ValidationBehavior` ou validações manuais em Queries
`NotFoundException`**404 Not Found**Recurso não existe — `NotFoundException.ForResource("{Entidade}", id)`
`BusinessException`**400 Bad Request**Regra de negócio violada — `new BusinessException("Status inválido", "INVALID_STATUS")`
`ConflictException`**409 Conflict**Conflito com o estado atual (duplicidade, transição inválida) — `new ConflictException("{Entidade}", "msg")`
`UnauthorizedAccessException` (built-in)**401 Unauthorized**Trata pelo pipeline de auth, não pelo middleware

> ✅ Todas as exceções acima vêm de FuncefEssenciais.Exceptions e são mapeadas pelo GlobalExceptionMiddleware — inclusive ConflictException → 409 nativamente (não é preciso classe local nem CustomExceptionMappings). Fonte: funcef-componentes/lib-back-essenciais/FuncefEssenciais/Exceptions/ConflictException.cs e .../Http/Middleware/GlobalExceptionMiddleware.cs.

ConflictException (da lib) — API disponível:

using FuncefEssenciais.Exceptions;

// Construtor recurso + mensagem (o mais usado nos Services):
throw new ConflictException("{Entidade}", "Já existe um registro com este {campo}");

// Factories:
throw ConflictException.ForResource("{Entidade}", id);                 // "Recurso '{Entidade}' com identificador '{id}' já existe ou está em conflito"
throw ConflictException.ForResourceWithMessage("{Entidade}", "msg");   // recurso + mensagem custom
```

Expõe NomeRecurso e Identificador; o middleware usa NomeRecurso na resposta 409.

> CustomExceptionMappings continua útil para mapear exceções próprias do domínio a status específicos; não é necessário para ConflictException (já é 409 na lib).

6.9 Quando usar qual exceção

CenárioExceçãoStatus
Recurso não existe (consulta)`NotFoundException.ForResource("{Entidade}", id)`404
Já existe registro com mesmo campo único`new ConflictException("{Entidade}", "Já existe um registro com este {campo}")`409
Tentar deletar registro com dependentes`new ConflictException("{Entidade}", "Não é possível excluir registro com dependentes")`409
Transição de status inválida`new BusinessException("Não é permitido aprovar registro já entregue", "INVALID_TRANSITION")`400
Campo obrigatório vazio no POST(não escrever manualmente) `ValidationException` automática400

6.10 Exemplos reais

Lançar NotFoundException no Handler de Query

public async Task<{Entidade}Response> Handle(Get{Entidade}ByIdQuery query, CancellationToken ct)
{
    var entity = query.Incluir{Navegacao}
        ? await _service.GetByIdWithAutoIncludesAsync(query.Id, ct)
        : await _service.GetByIdAsync(query.Id, ct);

    if (entity is null)
        throw NotFoundException.ForResource("{Entidade}", query.Id);

    return entity.MapTo<{Entidade}, {Entidade}Response>();
}
```

Lançar ConflictException no Service

if (!string.IsNullOrEmpty(request.Email)
    && await _repository.ExistsAsync(c => c.Email == request.Email, cancellationToken: ct))
{
    throw new ConflictException("{Entidade}", "Já existe um registro com este email");
}
```

Service que delega o "404" para o próprio caller

UpdateAsync e ValidateAndDeleteAsync lançam NotFoundException diretamente — o Handler permanece livre de if (entity == null):

public virtual async Task<{Entidade}> UpdateAsync(long id, {Entidade}Request request, CancellationToken ct = default)
{
    var entity = await _repository.GetByIdAsync(id, cancellationToken: ct)
        ?? throw NotFoundException.ForResource("{Entidade}", id);
    // ...
}
```

6.11 Forma do payload de erro

A resposta de erro retornada pelo GlobalExceptionMiddleware segue um shape padronizado (definido pelo componente). Em produção, evita expor stack trace ou mensagens de banco.

// 404
{
  "errorCode": "NOT_FOUND",
  "message": "{Entidade}: o recurso com identificador '…' não foi encontrado.",
  "traceId": "00-..."
}

// 409
{
  "errorCode": "CONFLICT",
  "message": "{Entidade}: Já existe um registro com este email",
  "traceId": "00-..."
}

// 400 (BusinessException)
{
  "errorCode": "INVALID_TRANSITION",
  "message": "Não é permitido aprovar registro já entregue",
  "traceId": "00-..."
}
```

Para ValidationException, o payload inclui a lista de erros campo a campo:

{
  "errorCode": "VALIDATION_FAILED",
  "message": "Um ou mais campos são inválidos.",
  "errors": {
    "Request.Nome": ["O campo 'nome' é obrigatório."],
    "Request.Email": ["O e-mail informado é inválido."]
  },
  "traceId": "00-..."
}
```

6.12 Boas práticas (resumo)

  • ✅ Em Commands: declarar Validator (com helpers FUNCEF sempre que possível).
  • ✅ Em Queries: validar no Handler apenas o que for regra, não tipo/range (deixar pra Validator se a Query for crítica).
  • ✅ Em Services: lançar exceção tipada — nunca devolver null/Result<> para sinalizar erro de domínio.
  • ✅ Em Handlers: deixar a exceção subir. Só usar try/catch para BeginAsync/CommitAsync/RollbackAsync (vide BE-04-Persistencia-Transacoes §4.7).
  • ❌ Não escrever throw new Exception(...) genérico — sempre tipo específico.
  • ❌ Não inventar HTTP code em controller (return BadRequest(...)) — sempre via exceção tipada.
  • ❌ Não engolir exceção com try { … } catch { /* swallow */ }.

6.13 Anti-padrões frequentes

Anti-padrãoPor que é proibidoCorreção
`return BadRequest(ModelState)` no controllerInconsistência de respostas; bypass do middlewareDeixar a exceção subir; `ValidationBehavior` cuida
`try { … } catch (Exception ex) { return StatusCode(500, ex.Message) }`Vazamento de detalhes internosSem `try/catch`; middleware mascara em prd
`throw new Exception("Email duplicado")`Sem tipo, sem código`throw new ConflictException("{Entidade}", "Email duplicado")`
`if (entity == null) return NotFound()` em controllerLógica espalhada`throw NotFoundException.ForResource(...)` no Handler
Validar `Guid.Empty` manualmenteRepetição`this.RuleForRequiredId(x => x.Id, "id")`
Sem Validator porque "é simples"Inconsistência em PR review**Sempre** criar Validator para Command, mesmo que com 1 regra
