5.1 Provedor de identidade

ItemValor
Identidade**Azure Entra ID** (ex-Azure AD)
Protocolo (fluxo interativo)OAuth 2.0 com PKCE — `response_type=code`
Protocolo (M2M)OAuth 2.0 — Client Credentials
Formato de tokenJWT Bearer assinado pelo Entra ID
Componente FUNCEF`FUNCEF.Autenticacao`

Toda a autenticação é provida pelo FUNCEF.Autenticacao — não há código aplicacional para login, callback, refresh ou validação de token. O microserviço apenas:

  1. Liga o componente em Program.cs (builder.Services.AddFUNCEFAuthentication(configuration))
  2. Registra os controllers de auth (AddFuncefAuthControllers())
  3. Marca endpoints com [FuncefAuthorize]

Decisão registrada em Decisoes-Arquiteturais ADR-009.

5.2 Fluxo OAuth 2.0 + PKCE (usuário interativo)

sequenceDiagram
    autonumber
    participant Br as Browser
    participant API as {Servico}.API
    participant EID as Azure Entra ID

    Br->>API: GET /auth/login
    API->>API: Gera code_verifier, code_challenge, state, nonce<br/>(armazena na Session)
    API-->>Br: 302 → Entra ID (authorize?…code_challenge…state)
    Br->>EID: GET /authorize
    EID-->>Br: tela de login
    Br->>EID: credenciais + MFA
    EID-->>Br: 302 → /auth/callback?code=…&state=…
    Br->>API: GET /auth/callback?code=…&state=…
    API->>API: Valida state e nonce da sessão
    API->>EID: POST /token<br/>(code, code_verifier, client_secret)
    EID-->>API: id_token, access_token, refresh_token
    API->>API: Persiste sessão, emite cookie .{Servico}.Session<br/>(HttpOnly, Secure, SameSite=None)
    API-->>Br: 302 → /login-success.html
```

Configuração em appsettings.json:

"Auth": {
  "Provider": "EntraId",
  "LoginPage": "/login.html",
  "SuccessPage": "/login-success.html",
  "EntraId": {
    "TenantId": "", "ClientId": "", "ClientSecret": "",
    "Audience": "",
    "Instance": "https://login.microsoftonline.com/",
    "ValidateIssuer": true, "ValidateAudience": true,
    "RedirectUri": "", "PostLogoutRedirectUri": "",
    "Scope": "openid profile email User.Read",
    "EnablePkce": true,
    "ResponseType": "code",
    "AllowM2M": true
  }
}
```

appsettings.Development.json (apenas overrides):

"Auth": {
  "EntraId": {
    "RedirectUri": "https://localhost:{PORTA}/auth/callback",
    "PostLogoutRedirectUri": "https://localhost:{PORTA}/login.html"
  }
}
```

TenantId, ClientId, ClientSecret, Audience em dev vêm de dotnet user-secrets ou do appsettings.Development.json local não commitado.

> ⚠️ Audience depende da versão do access token do App Registration (api.requestedAccessTokenVersion no manifesto — confira com az ad app show --id {clientId} --query api.requestedAccessTokenVersion):

>

> - v2 (padrão dos app registrations novos): o aud do access token é o ClientId GUID puro → configure Audience com o GUID. O AudienceHelper da lib deriva e aceita também api://{clientId} a partir do GUID, mas nunca deriva o inverso (decisão de segurança).

> - v1 (null/1): o aud vem como api://{clientId} → configure api://{clientId} (fecha replay de id_token).

>

> Sintoma do erro: Audience: "api://{clientId}" com token v2 ⇒ 401 em todos os endpoints, sem WWW-Authenticate e sem log óbvio. Diagnóstico: decodifique o payload do token e compare o aud com a config. Origem: migração do app registration do GAP (2026-07-10).

5.3 Fluxo Client Credentials (M2M)

sequenceDiagram
    participant App as Aplicação externa
    participant API as {Servico}.API
    participant EID as Azure Entra ID

    App->>API: POST /auth/m2m/token<br/>{ clientId, clientSecret, scope }
    API->>EID: POST /token (grant_type=client_credentials)
    EID-->>API: access_token (JWT)
    API-->>App: { access_token, expires_in, token_type=Bearer }

    Note over App,API: Subsequente
    App->>API: GET /{Recurso}<br/>Authorization: Bearer access_token
    API->>API: ValidateToken (audience, issuer, signature)
    API-->>App: 200 / 401 / 403
```

Habilitado via Auth:EntraId:AllowM2M = true. O endpoint POST /auth/m2m/token é registrado por AddFuncefAuthControllers().

> 🔸 Credencial do próprio app (Auth:EntraId:CredentialType) — usada nos fluxos em que a API se autentica no Entra (callback do authorization code e client_credentials app-only, ex.: Graph). Valores (EntraCredentialType): ClientSecret (default; direto ou via ClientSecretKeyName do KV), Certificate (client_assertion RS256; certificado no KV via ClientCertificateKeyName/FUNCEF.Cofre ou store local via ClientCertificateThumbprint) e ManagedIdentity (WIF — token da MI para api://AzureADTokenExchange como client_assertion federado; requer Federated Identity Credential no App Registration).

>

> ⚠️ ManagedIdentity só funciona rodando no Azure. Em dev, o DefaultAzureCredential cai na credencial do az login (usuário) e o Entra rejeita token de usuário como client_assertion federado (AADSTS700222) — a falha aparece como "Falha ao adquirir token app-only (HTTP 401)" e, com PDP, vira fail-closed (Deny). Dev secretless ⇒ CredentialType=Certificate no appsettings.Development.json; fallback ⇒ ClientSecret em user-secrets.

5.4 Sessão (PKCE state/nonce)

Para guardar state e nonce durante o redirect OAuth, ASP.NET Core Session em memória distribuída:

builder.Services.AddDistributedMemoryCache();
builder.Services.AddSession(options =>
{
    options.IdleTimeout = TimeSpan.FromMinutes(30);
    options.Cookie.HttpOnly = true;
    options.Cookie.IsEssential = true;
    options.Cookie.SameSite = SameSiteMode.None;
    options.Cookie.SecurePolicy = CookieSecurePolicy.Always;
    options.Cookie.Name = ".{Servico}.Session";
});
```
SettingRazão
`HttpOnly = true`Impede acesso via JavaScript (mitiga XSS)
`Secure = Always`Cookie só sai por HTTPS
`SameSite = None`Necessário para o redirect cross-site do Entra ID (com `Secure=true` é seguro)
`IdleTimeout = 30min`Sessão de PKCE expira em 30min de inatividade

Aviso **Produção multi-instância**

Em produção com múltiplas instâncias da API, **substituir `AddDistributedMemoryCache()` por Redis** — caso contrário, instâncias diferentes não compartilham a sessão e o callback falha. Usar o mesmo Redis de `NoSql:RedisCache` com `Auth:RefreshToken:StorageType = "Redis"`.

5.5 Refresh tokens

A **política de segurança** do refresh token é **fixa no componente** (CMP-03): rotação, revogação em reuso e algoritmo de hash são invariantes forçados (não configuráveis pelo microserviço), e os lifetimes têm clamp de faixa segura. O consumidor fornece apenas o **segredo** (Key Vault) e a **infra** (Redis via `FUNCEF.NoSql`):

"NoSql": {
  "Redis": {
    "ConnectionStringFromKeyVault": { "Enabled": true, "SecretName": "api-redis-conn" },
    "EnableSsl": true
  }
},
"Auth": {
  "RefreshToken": {
    "Enabled": true,
    "StorageType": "Redis",
    "SigningKeyFromKeyVault": { "Enabled": true, "SecretName": "glb-auth-refresh-jwt" }
  }
}
```

**Caminho canônico (api-template-base):** registrar `AddRedisCache(configuration, "NoSql:RedisCache")` **antes** de `AddFUNCEFAuthentication` — o store de refresh/revogação reaproveita `ICacheStore`. Alternativa da lib: `AddFuncefSecurityRedis` mapeia a seção opcional `Auth:Redis` → `AddRedisCache` (mesmo contrato `ConnectionStringFromKeyVault`); preferir **`NoSql:RedisCache`** para um único Redis compartilhado (cache + refresh).

Em dev (`appsettings.Development.json`): `"StorageType": "InMemory"`. O `SigningKey` (≥ 32 chars) é obrigatório e resolvido do Key Vault via `SigningKeyFromKeyVault` — propagado **para dentro** do `IOptions` consumido pelo serviço.

Nota **Comportamento na renovação**

  • **Revalidação no Entra:** a renovação revalida os privilégios via hook plugável `IRefreshClaimsRevalidator`. O default é no-op; em produção registre um revalidador real (Graph app-only pelo `oid`).
  • **Limite LRU:** ao exceder `MaxActiveTokens*`, revoga apenas o token **mais antigo** (não derruba todas as sessões).
  • **Fail-fast do storage:** `StorageType = Redis` sem `ICacheStore` registrado **falha no startup** (não degrada silenciosamente para InMemory).
  • **Rotação:** consumo único; a atomicidade total no Redis depende de um lock plugável (`IRefreshTokenRotationLock`), pois o `ICacheStore` do FUNCEF.NoSql não expõe *set-if-not-exists* nativo — sem o lock, é *best-effort* (documentado).

5.6 Autenticação e conformidade Entra — `[FuncefAuthorize]`

[!IMPORTANT]

**`[FuncefAuthorize]` — autenticação + conformidade Entra e, com `Acao`, autorização no PDP (CMP-03)**

Sem `Acao`, `[FuncefAuthorize]` exige um token válido do Entra ID e valida **conformidade de tenant** (`EntraTenantType.Any` / `Internal` / `External`); roles/scopes declarados são **opcionais** em **OR**. Com **`Acao`**, o atributo **também autoriza** a ação canônica no **PDP RBAC/ABAC do GAP** (ver nota abaixo). Regras de domínio pontuais (não governadas pelo GAP) continuam na aplicação.

Marcação por método (ou controller) que exige token válido e conformidade de tenant:

[HttpPost]
[FuncefAuthorize]                                   // qualquer tenant conforme (default)
public async Task<IActionResult> Create([FromBody] {Entidade}Request request, CancellationToken ct = default)
{
    var result = await _mediator.Send(new Create{Entidade}Command { Request = request }, ct);
    return ApiCreated(result);
}
```
// Conformidade de tenant explícita + roles/scopes OPCIONAIS (avaliados em OR)
[FuncefAuthorize(TenantType = EntraTenantType.Internal, Roles = "Gestor", Scopes = "api.write")]
```

[!IMPORTANT]

**`[FuncefAuthorize(Acao = "...")]` autoriza no GAP (PDP).** Além dos modos acima, informar a propriedade **`Acao`** faz o atributo, após a conformidade Entra, **autorizar a ação canônica no PDP RBAC/ABAC do GAP** via `IFuncefAuthorizationClient` (com tokens de rota `{sistema}`, fail-closed). Requer registrar o cliente do PDP (`AddFuncefAuthorizationClient` HTTP, ou o cliente in-process no próprio `api-ms-gap`). Ver [[CMP-03-Autenticacao]].

// Autentica + autoriza a ação no PDP (por sistema via token de rota {sistema})
[FuncefAuthorize(Acao = "Funcef.<Sistema>/{sistema}/recurso/write")]
```

[!NOTE]

**Onde fica a autorização de negócio**

Autorização governada por **permissões do GAP** (RBAC/ABAC) → `[FuncefAuthorize(Acao = ...)]` (o PDP decide). Regras de domínio pontuais como "só o dono do recurso edita" continuam no Handler/Service da aplicação (BE-03).

Cobertura típica:

ControllerCobertura
Controllers de domínio (`{Entidades}Controller`)**Todos** os métodos: `[FuncefAuthorize]` (autenticação + conformidade Entra)
Endpoints de `/auth/*`Mistos (login e callback são públicos; user/me etc. são autenticados) — registro feito por `AddFuncefAuthControllers()`
`/health*`, `/info`**Públicos** (não exigem token)
`/swagger`**Público** em Dev/Hml quando `Swagger:Enabled = true`

5.6.1 Tokens de Acesso (PAT) — consumidor

Um **PAT** (Personal Access Token) do GAP é um **token opaco** `gap_…` (não é JWT): não há validação

local. Um serviço que aceita PAT valida-o por **introspecção** no GAP. Habilite (opt-in) **após**

`AddFUNCEFAuthentication`:

builder.Services.AddFUNCEFAuthentication(builder.Configuration);
builder.Services.AddFuncefPatAuthentication(builder.Configuration);   // seção Auth:Pat
```

O que a extensão registra:

  • **Smart-forwarding** (policy scheme `Funcef.Smart`, vira o scheme padrão): `Authorization: Bearer gap_…`

→ handler `Pat`; qualquer outro `Bearer` → JWT do Entra. O mesmo endpoint aceita PAT e Entra.

  • **Introspecção**: `POST {Auth:Pat:BaseUrl}{Auth:Pat:IntrospectionPath}` (padrão

`/autorizacao/introspect`, corpo `{ "token": "gap_..." }`). O serviço se autentica como **M2M

Entra (client-credentials)** usando a **própria app** (`Auth:EntraId`), que precisa ter a **app role

`Gap.Introspect`** no GAP; escopo `.default` em `Auth:Pat:IntrospectionScope`.

  • **Cache** curto em processo (`Auth:Pat:CacheTtlSeconds`, padrão 60s; só resultados ativos). **Fail-closed**:

erro/indisponibilidade ⇒ PAT inativo (401). Revogação observável após o TTL.

  • **Identidade** materializada com as claims canônicas do GAP: `auth_method=pat`, `oid`, `pat_scope`

(`read-only`/`full-access`), `pat_sistema`, `pat_perm` (multivalorada); `AuthenticationType = "Pat"`.

**Teto do PAT:**

  • Endpoints com `[FuncefAuthorize(Acao = "...")]` → o **PDP do GAP** aplica o teto completo (sistema +

verbo + subconjunto granular); a lib só propaga o `Bearer gap_…`.

  • Endpoints com só `[FuncefAuthorize]` (sem `Acao`) → a lib aplica o **teto por verbo HTTP**: escopo

`read-only` só permite métodos seguros (GET/HEAD/OPTIONS); `full-access` passa; caso contrário 403

(`code: PAT_SCOPE_DENIED`).

Config `Auth:Pat` (obrigatórios quando habilitado: `BaseUrl`, `IntrospectionScope`):

"Auth": {
  "Pat": {
    "Enabled": true,
    "BaseUrl": "https://gap.funcef.com.br",
    "IntrospectionPath": "/autorizacao/introspect",
    "IntrospectionScope": "api://<gap-client-id>/.default",
    "CacheTtlSeconds": 60,
    "TimeoutMs": 2000,
    "ForwardedScheme": "Bearer"
  }
}
```

[!NOTE]

**Decisão em lote:** o cliente do PDP consome o endpoint de **lote real** `POST /autorizacao/decisao/lote`

(`{ "actions": [...] }` → `{ "results": [...] }`) numa única chamada; caminho parametrizável em

`Auth:Autorizacao:BatchDecisionPath`. `FuncefDecisao` expõe `PolicyCode` (diagnóstico ABAC).

5.6.2 Autorização granular por sistema — onboarding no GAP e menu efetivo

Um sistema que usa `[FuncefAuthorize(Acao = "...")]` e/ou o menu efetivo (`GET /auth/menu/me`) precisa

estar **cadastrado no GAP**. O contrato do ecossistema:

  1. **PEP encaminha o Bearer do usuário** ao PDP (nunca token próprio) — e o GAP aceita a audience do

sistema chamador porque os `ID_CLIENTE_APLICACAO` dos sistemas **ativos** de `TB_SISTEMAS` formam a

lista de confiança de audiences do PDP (validador por sistema, cache 60s, fail-closed; issuer e

assinatura seguem validados normalmente). Desativar o sistema no GAP revoga a audience.

  1. **Ações canônicas** seguem `Funcef.//`: **`read`** em GET,

**`write`** em POST/PUT/PATCH/DELETE — um par por recurso do sistema, mais a **wildcard

administrativa `Funcef./**`** (sensível) para o grupo admin. Anote cada action do

controller com a `Acao` correspondente.

  1. **Onboarding no GAP** (registros mínimos; em dev via script idempotente, em ambientes promovidos

via changeset Liquibase no repo do GAP):

- Sistema (`TB_SISTEMAS`): código PascalCase, app registration (ClientId), área, link principal;

- Permissões (`TB_PERMISSOES`): pares read/write por recurso + wildcard;

- Grupo de acesso (`TB_GRUPOS_ACESSO`): espelho do grupo de segurança do **Entra** (objectId) por

sistema + vínculo grupo→permissão (`TB_GRUPO_ACESSO_PERMISSAO`);

- Menu (`TB_ITENS_MENU`): dois níveis — seções (raiz, sem rota/permissão) e itens (rota + a

permissão de **leitura** que guia a visibilidade).

  1. **Menu efetivo no consumidor**: `GET /auth/menu/me` retorna a árvore podada pelo permission-set do

usuário no sistema **fixado por `Auth:Autorizacao:CodigoSistema`** (config; sem override por query —

isolamento por sistema). Fail-closed = `"itens": []`, nunca erro — as três causas de menu vazio e o

ajuste de `TimeoutMs` estão no [BE-11](../operacao/BE-11-Troubleshooting.md).

[!IMPORTANT]

**Fail-closed muda o custo de configuração ausente.** Com `Acao` nos controllers, a seção

`Auth:Autorizacao` (com `BaseUrl` e `CodigoSistema`) passa a ser **obrigatória em todos os

ambientes** — sem ela, todo endpoint com `Acao` responde 403 e o menu responde 503

(`AUTHORIZATION_CLIENT_NOT_CONFIGURED`).

5.8 Auditoria de acesso (`IAccessAuditService`)

[!IMPORTANT]

**Auditoria de acesso vive em **Oracle**, não em MongoDB (CMP-03)**

No `FUNCEF.Autenticacao` atual, a auditoria de tentativas de login (sucesso e falha) é persistida em **Oracle** via `IAccessAuditService`, na tabela **`LOG_AUDIT.Acesso_LOG`**. O MongoDB **não é mais** usado para isso. A seção de configuração passou de `Auth:AccessAudit` para **`Auth:Audit`**.

Toda tentativa de login (sucesso e falha) é registrada em Oracle:

"Auth": {
  "Audit": {
    "Enabled": true,
    "LogSuccessfulAccess": true,
    "LogFailedAccess": true,
    "IncludeClaims": true,
    "IncludeRequestInfo": true,
    "IncludeClientIp": true,
    "IncludeUserAgent": true,
    "RetentionDays": 90,
    "IgnoredPaths": [
      "/health", "/healthz", "/ready", "/metrics", "/swagger"
    ]
  }
}
```

O registro de `IAccessAuditService` é feito pelo próprio `AddFUNCEFAuthentication(configuration)` — não há mais `AddMongoDbDocumentStore(...)` para auditoria de acesso. A connection string Oracle dedicada à auditoria mora no Key Vault (§5.13, `AuditOracle`).

[!NOTE]

**Auditoria de acesso ≠ auditoria de entidade**

Esta seção trata de **acesso/login** (Oracle, `LOG_AUDIT.Acesso_LOG`). A auditoria de **mudança de entidade** é responsabilidade do ORM, via `[Auditable]` + interceptor `FUNCEF.ORM.Audit` (BE-04). O antigo `EntityAudit`/`IEntityAuditService` do `FUNCEF.Autenticacao` foi **removido** (2026-06-16).

Em dev: `Auth:Audit:Enabled = false` para reduzir ruído.

5.10 CORS restrito (sem wildcard)

[!IMPORTANT]

**Regra dura — CORS nunca usa `"*"` fora do Dev**

A FUNCEF autentica com **cookie de sessão + credenciais** (`AllowCredentials`, §5.4). A especificação CORS **proíbe** combinar `AllowAnyOrigin()` (`*`) com `AllowCredentials()` — o browser rejeita. Portanto **toda origem é explícita**, inclusive em Dev (lista de `localhost`). Wildcard em Hml/Prd é **bloqueado por fail-fast no startup**.

Caminho canônico (api-template-base / FUNCEF.Essenciais):

services.AddCorsPolicyWithConfiguration(environment, configuration);
// Lê Cors:Politica + Cors:OriginsPermitidas (BE-08 §8.3)
```
"Cors": {
  "Politica": "Production",
  "OriginsPermitidas": [ "https://app.funcef.com.br" ],
  "AllowCredentials": false
}
```

Configuração por ambiente:

Ambiente`Cors:Politica` / `Cors:OriginsPermitidas`
Dev`"Development"` — lista explícita de `localhost` (ex.: `["https://localhost:3000"]`) — **nunca** `["*"]`
Hml / Prd`"Production"` + lista explícita das origens reais do front

[!WARNING]

**Nunca relaxar**

  • **Não** usar `AllowAnyOrigin()`, nem `SetIsOriginAllowed(_ => true)`, nem refletir o header `Origin` da requisição — equivalem a `*` com credenciais e abrem CSRF cross-origin.
  • Restringir métodos ao necessário (`WithMethods`) em vez de `AllowAnyMethod()`.
  • Mudança na lista de origens é alteração de segurança: registrar no PR.

5.10.1 Cabeçalhos de segurança (HTTP security headers)

Todo microserviço FUNCEF responde com um conjunto fixo de **security headers**. Não há dependência externa: um middleware curto adiciona os headers, e `UseHsts()` entra no pipeline fora do Dev.

HeaderValor padrãoPor quê
`Strict-Transport-Security``max-age=31536000; includeSubDomains` (via `UseHsts()`, **só Hml/Prd**)Força HTTPS no browser; nunca em Dev (quebra `localhost` http).
`X-Content-Type-Options``nosniff`Impede MIME sniffing.
`X-Frame-Options``DENY`Anti-clickjacking (back-stop do CSP `frame-ancestors`).
`Referrer-Policy``strict-origin-when-cross-origin`Não vaza URL completa para terceiros.
`Content-Security-Policy`API JSON: `default-src 'none'; frame-ancestors 'none'`. Páginas servidas de `wwwroot` (login/dashboards): política explícita por serviço.Reduz superfície de XSS/injeção.
`Permissions-Policy``geolocation=(), camera=(), microphone=()`Desliga APIs de browser não usadas.
`X-Powered-By` / `Server`**removidos**Não expor stack/versão.
// Infrastructure/Middleware/SecurityHeadersMiddleware.cs — sem dependência externa
public sealed class SecurityHeadersMiddleware(RequestDelegate next)
{
    public async Task InvokeAsync(HttpContext context)
    {
        var h = context.Response.Headers;
        h["X-Content-Type-Options"] = "nosniff";
        h["X-Frame-Options"] = "DENY";
        h["Referrer-Policy"] = "strict-origin-when-cross-origin";
        h["Permissions-Policy"] = "geolocation=(), camera=(), microphone=()";
        h["Content-Security-Policy"] = "default-src 'none'; frame-ancestors 'none'";
        h.Remove("X-Powered-By");
        h.Remove("Server");
        await next(context);
    }
}
```
// Program.cs
if (!app.Environment.IsDevelopment())
    app.UseHsts();                 // STS só fora do Dev
app.UseSecurityHeaders();          // extension que registra o middleware acima
```

[!NOTE]

**CSP para páginas HTML servidas pelo serviço**

APIs que retornam só JSON usam o CSP restritivo acima. Quando o serviço serve `wwwroot/login.html`/dashboards (§5.12 `UseStaticFiles`), defina um CSP explícito (`script-src`/`style-src` com nonce/hash) por serviço — `default-src 'none'` sozinho quebra a página.

5.11 Rate limiting

Implementação canônica via **`FUNCEF.Essenciais`** (`RateLimitingMiddleware` + `[RateLimit]`), com contadores **distribuídos** no Redis (`ICacheStore` registrado por `AddRedisCache` antes do pipeline). **Não** usar `Microsoft.AspNetCore.RateLimiting` built-in nem lógica inline em controllers.

Configuração global (`appsettings.json`)

Padrão: **100 req/min por IP**.

"RateLimiting": {
  "PermitLimit": 100,
  "Window": "00:01:00",
  "Strategy": "ByIp",
  "FailOpenWhenCacheUnavailable": true,
  "ExcludedPaths": [ "/health", "/info", "/swagger" ]
}
```
ParâmetroValor padrãoObservação
`PermitLimit`100Requisições por janela
`Window``00:01:00`Janela fixa (`TimeSpan`)
`Strategy``ByIp``ByIp`, `ByUser`, `ByEndpoint`, `ByIpAndEndpoint`, `ByUserAndEndpoint`
`ExcludedPaths`—Prefixos ignorados (ex.: `/health` isenta `/health/ready`)
`AllowedPaths`—Se preenchido, limita **só** essas rotas (wildcard `/*`)
`FailOpenWhenCacheUnavailable``true``true` = libera se Redis indisponível (warning no log); `false` = 503 fail-closed
Status code429Too Many Requests + header `Retry-After` + `X-RateLimit-*`

Ajustar por serviço editando a seção `RateLimiting` no `appsettings.{Env}.json`. O middleware lê a config via `app.UseRateLimiting(app.Configuration)` — **não há** registro em `builder.Services`.

Pipeline

// ApiPipeline — ordem BE-05 §5.12
app.UseRateLimiting(app.Configuration);
app.UseAuthentication();
app.UseAuthorization();
```

**Pré-requisitos operacionais:** Redis (`CacheRegistration` / `AddRedisCache`) registrado; com `Strategy: ByIp` atrás de proxy/ingress, `Auth:TrustForwardedHeaders = true` (senão todos os clientes compartilham o IP do proxy).

Limite por endpoint (opcional)

Para operações sensíveis (ex.: POST de escrita), complementar o global com atributo **após autenticação**:

using FuncefEssenciais.Http.Attributes;
using FuncefEssenciais.Http.Middleware;

[RateLimit(permitLimit: 5, windowSeconds: 300, strategy: RateLimitStrategy.ByUser)]
[HttpPost("incluir")]
public IActionResult Incluir(...) { ... }
```

O middleware global e o `[RateLimit]` usam contadores independentes — o endpoint fica **mais restrito**, não menos.

Checklist operacional (deploy)

  • [ ] `NoSql:RedisCache` configurado e `ICacheStore` registrado (`CacheRegistration` antes de `AddFUNCEFAuthentication`).
  • [ ] Health check de Redis verde (`/health/ready`).
  • [ ] Atrás de ingress/proxy: `Auth:TrustForwardedHeaders = true` com proxy confiável.
  • [ ] `RateLimiting:Strategy` coerente com o cenário (`ByIp` global; `ByUser` no `[RateLimit]` de endpoints sensíveis).
  • [ ] `ExcludedPaths` não expõe `/health/*` publicamente no ingress externo (probe ready amplifica carga).
  • [ ] Monitorar log `"Rate limiting desabilitado: cache store indisponível"` — indica fail-open ativo.
  • [ ] Em produção crítica, avaliar `FailOpenWhenCacheUnavailable: false` (503 enquanto Redis estiver fora).

5.12 Pipeline de segurança — ordem dos middlewares

A ordem dos middlewares relativos a segurança é **fixa** (decisão em [Decisoes-Arquiteturais](../_shared/Decisoes-Arquiteturais.md) ADR-013):

UseGlobalExceptionHandler              # mapeia exceções tipadas → HTTP
UseHttpsRedirection                    # força HTTPS
UseHsts                                # (Hml/Prd) Strict-Transport-Security — §5.10.1
UseSecurityHeaders                     # nosniff, X-Frame-Options, CSP, Referrer-Policy — §5.10.1
UseDefaultFiles + UseStaticFiles       # serve wwwroot/login.html, dashboards
UseSwaggerDocumentation (Dev/feature)  # Swagger em Dev (ou Hml com flag)
UseCors                                # antes de Session e auth
UseSession                             # estado PKCE
UseRateLimiting                       # FUNCEF.Essenciais — bloqueia abusos (Redis)
UseAuthentication                      # valida JWT Bearer
UseAuthorization                       # avalia [FuncefAuthorize]
MapHealthChecks                        # endpoints públicos
MapControllers                         # routing final
```

A ordem **não é negociável** — alterá-la pode causar:

  • CORS depois de Authentication → falha com 401 antes do preflight.
  • Authorization antes de Authentication → `User.Identity` sem claims, autorização rejeita tudo.
  • Rate limiter depois de Auth → abusos consomem CPU validando tokens.

5.13.1 Regras de configuração e propagação de segredos (padrão de componente)

Três invariantes que **toda lib FUNCEF** que expõe configuração e consome Key Vault deve seguir — como na `FUNCEF.Autenticacao`:

  1. **Segredo do Key Vault sempre via `IPostConfigureOptions`.** Resolver segredos apenas em uma cópia local no momento do registro **não** os entrega ao `IOptions` consumido por controllers/handlers em runtime — o que quebra cenários "só Key Vault" e pode **desligar silenciosamente** validações que dependem desses valores (foi o caso da conformidade de tenant do `[FuncefAuthorize]`). Registre um `IPostConfigureOptions` que resolve os `*KeyName` **para dentro** das opções resolvidas via DI.
  2. **Toda chave de configuração pertence a uma classe de options tipada e vinculada, sob o grupo do componente.** Nada de chaves lidas soltas de `IConfiguration["..."]` (config "fantasma": sem IntelliSense, sem validação, sem descoberta). Na `FUNCEF.Autenticacao` tudo vive sob **`Auth`** — inclusive `Auth:Autorizacao` (cliente do PDP), `Auth:Endpoints` (páginas/diagnóstico/proxy) e `Auth:M2M`.
  3. **Endpoints de diagnóstico atrás de um gate desligado por padrão.** Qualquer endpoint que decodifique token sem validar assinatura ou exponha configuração/claims só deve responder quando um flag explícito estiver ligado (`Auth:Endpoints:EnableDebugEndpoints = true`) — nunca ativo em produção.

5.15 Health check do Entra ID

Quando `Auth:EntraId:TenantId` está configurado:

var entraIdTenantId = builder.Configuration["Auth:EntraId:TenantId"];
if (!string.IsNullOrEmpty(entraIdTenantId))
    healthChecksBuilder.AddAuthenticationHealthChecks();
```

O check valida que o Entra ID está alcançável e responde — útil para `/health/ready`. Quando indisponível, o serviço pode ainda servir endpoints públicos mas não autentica.

5.16 Checklist de segurança para um novo microserviço

  • [ ] `Auth:Provider = "EntraId"`.
  • [ ] App Registration criado no Entra ID; `TenantId`, `ClientId`, `Audience` configurados por ambiente.
  • [ ] `ClientSecret` em `user-secrets` (dev) e Key Vault (hml/prd) — **nunca** em `appsettings.*.json`.
  • [ ] `Auth:EntraId:RedirectUri` aponta para `https://{host}/auth/callback` de cada ambiente.
  • [ ] `Cors:Politica` + `Cors:OriginsPermitidas` — lista **explícita** em todos os ambientes (inclusive Dev) — **nunca** `"*"`; fail-fast ativo em Hml/Prd (§5.10 / BE-08).
  • [ ] `UseSecurityHeaders()` no pipeline e `UseHsts()` em Hml/Prd; CSP definido por serviço se servir páginas de `wwwroot` (§5.10.1).
  • [ ] Rate limit: seção `RateLimiting` no appsettings; `UseRateLimiting` no pipeline; Redis (`ICacheStore`) ativo; `TrustForwardedHeaders` se atrás de proxy (§5.11 checklist operacional).
  • [ ] Refresh token `StorageType = Redis` em prd (via `NoSql:RedisCache` + `ICacheStore`; `SigningKeyFromKeyVault`); `InMemory` em dev. Política (rotação/reuso/lifetimes) é fixa no componente — não configurar. Em prd, registre um `IRefreshClaimsRevalidator` real (revalidação no Entra) e, para rotação atômica, um `IRefreshTokenRotationLock`.
  • [ ] Se usar `[FuncefAuthorize(Acao = "...")]`: `AddFuncefAuthorizationClient` registrado e **`Auth:Autorizacao:BaseUrl`** apontando o PDP (**obrigatória** — validada no startup); sistema **cadastrado e ativo no GAP** (§5.6.2 — audience do chamador só é aceita pelo PDP se o sistema estiver em `TB_SISTEMAS`).
  • [ ] Se usar o **menu efetivo** (`GET /auth/menu/me`): `Auth:Autorizacao:CodigoSistema` preenchido e menu cadastrado no GAP; `TimeoutMs` calibrado (default 800ms cancela a 1ª chamada fria — BE-11).
  • [ ] `Auth:Endpoints:EnableDebugEndpoints = false` em prd (endpoints de diagnóstico desligados); `Auth:Endpoints:TrustForwardedHeaders = true` só atrás de proxy confiável.
  • [ ] `Audience` conforme a **versão do access token** do App Registration (§5.2): **v2** (`requestedAccessTokenVersion=2`, padrão dos apps novos) ⇒ **ClientId GUID puro** (a lib deriva `api://`; `api://` configurado com token v2 dá 401 silencioso); **v1** ⇒ `api://{clientId}` (fecha replay de id_token).
  • [ ] Se o serviço aceita **PAT**: `AddFuncefPatAuthentication` registrado; `Auth:Pat:BaseUrl`/`IntrospectionScope` preenchidos; app do serviço com a app role **`Gap.Introspect`** no GAP (§5.6.1).
  • [ ] `Auth:Audit:Enabled = true` em hml/prd; `false` em dev (auditoria de acesso em Oracle via `IAccessAuditService`, tabela `LOG_AUDIT.Acesso_LOG`).
  • [ ] Cookie de sessão renomeado para `.{Servico}.Session`.
  • [ ] Em produção multi-instância, sessão movida para Redis (não `DistributedMemoryCache`).
  • [ ] Todos os endpoints de domínio têm `[FuncefAuthorize]`.
