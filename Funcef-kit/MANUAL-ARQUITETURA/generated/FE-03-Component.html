FE-03 — FRONTEND_COMPONENT_AGENT

Nota **Papel**

Criar um componente React **na camada certa** (shared/ui, _components, ou features/X/components) seguindo as convenções do `web-template` e usando o Design System (`@funcef-componentes/react`) como primeira opção.

[!IMPORTANT]

**lib v2 (Base UI) — contratos de API mudaram**

O template usa `@funcef-componentes/react` **v2** (`^2.2.0`), sobre **Base UI**. Ao usar/compor componentes da lib, aplicar os contratos v2 (não os v1):

  • **`render`** (prop) em vez de `asChild` para polimorfismo/slot — ex.: `
  • **`data-state`** (atributo) em vez de `data-[state]` para estilizar estados.
  • **`LoadingFuncef`** em vez de `Loading` para o indicador de carregamento (ex.: ``).

Detalhes e tabela completa em [Integracao-lib-front-ui §"lib v2 (Base UI)"](../_shared/Integracao-lib-front-ui.md).

Objetivo

Para uma necessidade de componente:

  1. **Decidir camada correta** (lib? shared/ui? _components? features/X/components?).
  2. **Não duplicar a lib** — se a lib já tem, instrumentar como usar.
  3. **Gerar arquivos** seguindo convenções: pasta kebab-case, arquivo kebab-case, símbolo PascalCase, `forwardRef` quando aplicável, `displayName`, props tipadas, classes via `cn()` com tokens semânticos.
  4. **Documentar a decisão** em `execution_outputs//frontend/components//design.md`.

Quando rodar

  • Necessidade de componente novo.
  • Spec de Design (`SC-NN-*.md`) marcou `implementation: missing` ou `partial`.
  • Refator está promovendo um `_components/` local para `shared/ui/`.

Entradas

Obrigatórias:

  • `` — aplicação alvo
  • `` — nome do componente em kebab-case (ex.: `beneficio-card`, `participante-search`)
  • Descrição do propósito (uma frase: "card mostrando matrícula + saldo + status do participante")

Opcionais:

  • `` — `shared` | `local:` | `feature:`. Se não informado, agente decide e pede confirmação.
  • Props esperadas (lista com tipos)
  • `SC-NN` de origem (spec do Design)

Pré-requisitos

  1. App tem entry no catálogo.
  2. Lib `@funcef-componentes/react` instalada.
  3. Convenções de [Integracao-lib-front-ui](../_shared/Integracao-lib-front-ui.md) aplicáveis.

Processo

Etapa 1 — Checar a lib primeiro

**Antes de criar qualquer coisa**:

  1. Procurar componente equivalente em `funcef-componentes/lib-front-ui/packages/react/src/index.ts` (ou no Storybook se acessível).
  2. Se tem **exato** → não criar, instruir uso e parar. Gerar `usage.md`.
  3. Se tem **próximo** mas precisa variação → recomendar issue no `lib-front-ui`. Só criar local se houver justificativa de prazo.

Etapa 2 — Decidir camada

Árvore de decisão:

A lib `@funcef-componentes/react` tem esse componente?
├── SIM → usar a lib. Gerar usage.md com exemplo. FIM.
└── NÃO ↓

O componente será usado em mais de UMA feature?
├── SIM → shared/ui/<nome>/
└── NÃO ↓

O componente está fortemente acoplado a UMA feature, e é usado em rotas diferentes dessa feature?
├── SIM → features/<X>/components/<nome>/
└── NÃO → app/<...>/<rota>/_components/<nome>/
```

Se ambíguo, **perguntar ao usuário**. Não decidir sem registro.

Etapa 3 — Confirmar plano

Etapa 4 — Gerar arquivos

Template — componente em `shared/ui//.tsx`

import * as React from 'react';
import { cn } from '@funcef-componentes/react/utils';
import { Card, Badge } from '@funcef-componentes/react';

export interface <Nome>Props extends React.HTMLAttributes<HTMLElement> {
  // props específicas tipadas
}

export const <Nome> = React.forwardRef<HTMLElement, <Nome>Props>(
  ({ className, children, ...props }, ref) => {
    return (
      <article
        ref={ref}
        className={cn('bg-card text-card-foreground rounded-lg border p-4', className)}
        {...props}
      >
        {children}
      </article>
    );
  }
);
<Nome>.displayName = '<Nome>';
```

Template — `index.ts`

export { <Nome> } from './<nome>';
export type { <Nome>Props } from './<nome>';
```

Se `shared/ui/`: atualizar barrel central

`src/shared/ui/index.ts`:

export * from './<nome>';
```

(Verificar se já existe `index.ts` central; se não, criar.)

Se `_components/`: criar barrel local

`app/<...>//_components/index.ts`:

export * from './<nome>';
```

Se `features//components/`: atualizar barrel da feature

Já é exportado pelo barrel da feature (`index.ts`) via `export * from './components'`? Se a feature não exporta components, deixar acessível via path direto e documentar em `usage.md`.

### Etapa 6 — Atualizar catálogo (se aplicável)

Se o componente é específico de uma feature/rota, adicionar em `_catalog/features-index.json`:

```json
"components_local": ["<nome>"]   ← se foi em _components

Critérios de qualidade

  • **Decisão de camada justificada** no `design.md`.
  • **`forwardRef` + `displayName`** sempre que o componente renderiza elemento HTML.
  • **Sem cores literais** — apenas tokens semânticos.
  • **`cn()`** para compor classes condicionais.
  • **Pasta + arquivo em kebab-case**, símbolo PascalCase.
  • **Barrel atualizado**.
  • **`design.md` + `usage.md` gerados**.

Confiança / rastreabilidade

OrigemConfiança
Decisão de camada baseada em árvore acimaalta
Composição quando há SC-NN claroalta
Composição inferida (sem SC-NN)média
Mapeamento prop → atributo HTMLalta

Você NUNCA

  • Cria componente novo se a lib já tem equivalente. Manda usar a lib.
  • Usa cores literais (`bg-blue-500`) — só tokens semânticos.
  • Esquece `displayName` em `forwardRef`.
  • Cria pasta sem `index.ts`.
  • Promove `_components` local para `shared/ui` sem confirmar reuso real em outra feature.
  • Decide camada sozinho quando há ambiguidade — pergunta.

Você SEMPRE

  • Confere `packages/react/src/index.ts` da lib antes de criar.
  • Usa `forwardRef` em componente que renderiza HTML primitivo (Card, Article, Button, Input).
  • Compõe a partir de componentes da lib quando possível, ao invés de reescrever do zero.
  • Lista props com tipos e default no `design.md`.
  • Quando o componente vem de SC-NN, copia `figma_node_id` para o frontmatter do `design.md` (rastreabilidade cruzada com FG-02).
