BE-01 — Visão Geral

1.1 Propósito

Um microserviço backend FUNCEF é uma API REST .NET 10 que:

  1. Expõe um conjunto coeso de endpoints HTTP para um domínio específico (ex.: cadastro de participantes, contábil, financeiro).
  2. Persiste em Oracle (banco corporativo) via FUNCEF.ORM (EF Core + Dapper híbrido).
  3. Autentica via Azure Entra ID (OAuth 2.0 + PKCE para usuários, Client Credentials para M2M).
  4. Resolve segredos via Azure Key Vault (FUNCEF.Cofre).
  5. Reporta telemetria via OpenTelemetry → Application Insights.
  6. Audita mudanças de entidade no Oracle (via interceptor FUNCEF.ORM.Audit, atributo [Auditable]) e tentativas de login também no Oracle (via IAccessAuditService do FUNCEF.Autenticacao, tabela LOG_AUDIT.Acesso_LOG).
  7. Opera atrás de proxy/ingress que termina TLS, exposto na porta 8080.
  8. Roda em Kubernetes com probes /health/live e /health/ready.

A documentação desta família descreve o padrão; o projeto funcef/api-template-base materializa esse padrão com um domínio didático para servir de referência viva.

1.2 Capacidades esperadas de qualquer microserviço FUNCEF

CapacidadeOnde se materializa
**CRUD completo via CQRS/Mediator**Pasta `Commands/{Entidade}/{Acao}/` + `Queries/{Entidade}/{Detalhe}/`
**Query paginada com busca e ordenação**`GetPagedAsync` em Service + `PagedRequest`/`PaginatedResult`
**Query com auto-include de navegação**`[AutoInclude]` em navegação + `GetByIdWithAutoIncludesAsync`
**Transação multi-entidade (EF Core)**Handler com `IUnitOfWork.BeginAsync / CommitAsync / RollbackAsync`
**Transação multi-entidade (Dapper)**Handler usa mesmo `IUnitOfWork`; Service usa `_repository.ExecuteAsync(sql, params)`
**Validação no pipeline do Mediator**`AbstractValidator` + `ValidationBehavior`
**Exceções tipadas → HTTP padronizado**`NotFoundException` (404), `BusinessException` (400), `ConflictException` (409, herda `BusinessException`, mapeada nativamente pela lib) + `GlobalExceptionMiddleware`
**Auditoria automática de entidades**`[Auditable("Recurso")]` + interceptor do `FUNCEF.ORM.Audit`
**Auditoria de acesso (login)**`IAccessAuditService` → Oracle (`LOG_AUDIT.Acesso_LOG`), registrado por `AddFUNCEFAuthentication`
**OAuth2 + PKCE interativo**`AddFuncefAuthControllers` (rotas `/auth/login`, `/auth/callback`, …)
**Client Credentials (M2M)**Endpoint `POST /auth/m2m/token`
**Refresh tokens em Redis**`AddRedisCache` (`NoSql:RedisCache`) + `Auth:RefreshToken:StorageType = "Redis"`
**Health checks com probes K8s**`/health`, `/health/live`, `/health/ready`, `/health/version`
**Telemetria estruturada**`ITelemetry` injetado; OpenTelemetry → App Insights
**Fail-fast em produção**`AddConfigurationValidation` aborta startup se config crítica inválida
**Containerização**`Dockerfile` multi-stage com `HEALTHCHECK` em `/health/live`
**Rate limiting por IP**`UseRateLimiting` (`FUNCEF.Essenciais`) — seção `RateLimiting` no appsettings (default 100 req/min)
**CORS configurável por ambiente**`Cors:Politica` + `Cors:OriginsPermitidas` no `appsettings.{Env}.json`

1.7 Decisões arquiteturais (resumo)

DecisãoEscolhaMotivação
Arquitetura macroClean Architecture (4 camadas)Isolamento de domínio, testabilidade, independência de frameworks
Padrão de aplicaçãoCQRS/Mediator + Service LayerHandler = orquestração + transação · Service = lógica + dados
ORMEF Core + Dapper híbridoEF para CRUD/transações · Dapper para SQL Oracle específico
Pipeline de validaçãoFluentValidation com `ValidationBehavior` no MediatorValidação antes do Handler; controllers ficam finos

1.8 O que NÃO está no padrão base

Não incluídoComo tratar quando precisar
Mensageria (Queue / Service Bus)Azure Queue Storage para fire-and-forget simples; Service Bus para pub/sub, dead-letter, sessions. Ver [Decisoes-Arquiteturais](../_shared/Decisoes-Arquiteturais.md) ADR-018
Background jobs / scheduling**Quartz.NET** (`FUNCEF.Jobs`) in-process; Azure Functions Timer Trigger quando desacoplado. Ver ADR-020
GraphQLNão está no padrão; manter REST salvo justificativa explícita
AutoMapper / MapsterNão — usar `[MapFrom]`/`[NestedMap]` do `FuncefORM.Mapping`
Repositórios específicos por entidadeUsar `IRepository` do `FUNCEF.ORM`; lógica vai no Service
Versionamento de API (`/v1/...`)Não implementar preventivamente. Versionar só em breaking change de contrato externo. Ver ADR-017
Multi-tenancyNão-padrão. Quando necessário: schema por tenant + ADR de serviço + aprovação arquitetura/DBA. Ver ADR-019

1.9 Sinais de saúde de um microserviço FUNCEF

Ao revisar (humano ou IA), verificar:

  • [ ] Existe Directory.Build.props com net10.0 + TreatWarningsAsErrors=true.
  • [ ] Existem 4 projetos (Domain, Application, Infrastructure, API) + 1 de testes.
  • [ ] Application não referencia Infrastructure.
  • [ ] Todos os Commands têm Validators.
  • [ ] Controllers herdam de BaseController e recebem IMediator + ITelemetry.
  • [ ] Nenhum Controller tem try/catch ou return BadRequest(...).
  • [ ] Nenhum Handler tem try/catch defensivo (apenas em transações multi-passo com Rollback).
  • [ ] Entidades sensíveis têm [Auditable("Recurso")].
  • [ ] Endpoints autenticados têm [FuncefAuthorize].
  • [ ] appsettings.json não contém segredos preenchidos.
  • [ ] Telemetry:ServiceName reflete o nome real do serviço (não cópia).
  • [ ] Cookie de sessão é .{Servico}.Session.
  • [ ] Cors:Politica + Cors:OriginsPermitidas definidos por ambiente (lista explícita inclusive Dev — nunca ["*"]; ver BE-05 §5.10).
  • [ ] Health checks com tags live/ready registrados conforme dependências reais.
  • [ ] Dockerfile referencia {Servico}.sln/{Servico}.slnx e expõe 8080.
  • [ ] Testes verdes (dotnet test).
