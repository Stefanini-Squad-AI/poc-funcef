FE-02 — FRONTEND_FEATURE_AGENT

Nota **Papel**

Scaffold de uma feature completa em `src/features//` seguindo o padrão observado em `web-template/src/features/tasks/`. Gera api (`client`/`endpoints`/`index`), hooks RQ, types, validators, components e barrel — pronto para uso por `app//page.tsx`. **Não gera `service.ts`**: os hooks chamam `Api` (que usa `api` de `@/core/api`) direto.

Objetivo

Para uma nova funcionalidade do usuário (domínio de negócio FUNCEF), criar:

src/features/<dominio>/
├── api/
│   ├── client.ts           ← objeto <dominio>Api com getAll/getById/create/update/delete via api<T>
│   ├── endpoints.ts        ← constantes/funções de URL
│   └── index.ts
├── hooks/
│   ├── use-<dominio>-query.ts    ← useQuery, useInfiniteQuery → chama <dominio>Api
│   ├── use-<dominio>-mutation.ts ← useMutation com invalidateQueries
│   └── index.ts
├── components/             ← criada vazia (será populada por FE-03)
├── types.ts                ← domain types + Create/Update partials
├── validators.ts           ← Zod schemas + safeParse helpers
└── index.ts                ← barrel
```

[!NOTE]

**Sem `service.ts`**

O template atual **não tem** classe `Service` estática. Regra de negócio/orquestração/transformação vive no **hook** (ou em util de `shared/lib`). Não recriar `service.ts`.

E atualiza o catálogo `_catalog/features-index.json` com a nova entrada.

Quando rodar

  • Necessidade de **nova feature** mapeada para um microsserviço FUNCEF.
  • Orchestrator FE-00 detectou que a feature solicitada não existe.
  • FE-01 marcou a feature como `draft` no catálogo.

Entradas

Obrigatórias:

  • `` — aplicação alvo (caminho do repo)
  • `` — nome da feature em kebab-case (ex.: `contribuicao`, `cadastro-participante`)
  • `` — nome do microsserviço backend (ex.: `api-ms-contribuicao`) — contexto de negócio; no template base o tráfego passa pelo **BFF único** `/api/bff` → `API_URL`.
  • Shape do tipo do domínio — campos + tipos. Se não informado, pedir confirmação ao usuário antes de prosseguir.

Opcionais:

  • Lista de endpoints (default: CRUD padrão — getAll, getById, create, update, delete)
  • ID de tela linkada (`SC-NN`) se a feature foi originada de spec de Design

Pré-requisitos

  1. App tem entry no `_catalog/features-index.json` (criar via FE-01 antes se necessário).
  2. Stack canônica instalada (validar pelo orchestrator).
  3. `src/core/api.ts` existe (sempre existe no template — não recriar).
  4. Microsserviço alvo confirmado pelo usuário. **Nunca inventar** nome de microsserviço.

Processo

Etapa 1 — Confirmar com usuário

Antes de criar, mostrar plano:

Plano de scaffold:
- Feature: contribuicao
- Microsserviço: api-ms-contribuicao (BFF único: /api/bff → API_URL server-only)
- Tipo principal: Contribuicao { id, participanteId, valor, competencia }
- Endpoints: GET /contribuicoes, GET /contribuicoes/:id, POST /contribuicoes, PUT /contribuicoes/:id, DELETE /contribuicoes/:id
- Schema Zod: contribuicaoSchema (com createContribuicaoSchema = omit({id}), updateContribuicaoSchema = partial)
- Arquivos criados: api/{client,endpoints,index}.ts, hooks/{use-X-query,use-X-mutation,index}.ts, types.ts, validators.ts, index.ts (SEM service.ts)
- Catálogo: entrada nova em <App>.features[]

Pode prosseguir?
```

Esperar confirmação. Se usuário ajustar campos/endpoints, refletir no plano antes de gerar.

`api/client.ts`

import { api } from '@/core/api';
import type { <Dominio>, Create<Dominio>Data, Update<Dominio>Data } from '../types';
import { <dominio>Endpoints } from './endpoints';

export const <dominio>Api = {
  getAll: () => api.get<<Dominio>[]>(<dominio>Endpoints.list),

  getById: (id: number | string) =>
    api.get<<Dominio>>(<dominio>Endpoints.byId(id)),

  create: (data: Create<Dominio>Data) =>
    api.post<<Dominio>, Create<Dominio>Data>(<dominio>Endpoints.create, data),

  update: (id: number | string, data: Update<Dominio>Data) =>
    api.put<<Dominio>, Update<Dominio>Data>(<dominio>Endpoints.update(id), data),

  delete: (id: number | string) =>
    api.delete<void>(<dominio>Endpoints.delete(id)),
};
```

`api` (de `@/core/api`, `createApi` da auth lib) aponta para o **BFF same-origin** `/api/bff`. Envelope FUNCEF normalizado e `401 → teardown` vêm da lib.

`validators.ts`

import { z } from 'zod';
// reusar fields atômicos quando aplicável:
// import { cpfField, emailField } from '@/shared/lib';

export const <dominio>Schema = z.object({
  id: z.number().int().positive(),
  // ... campos
});

export const create<Dominio>Schema = <dominio>Schema.omit({ id: true });
export const update<Dominio>Schema = create<Dominio>Schema.partial();

export type <Dominio>Validated = z.infer<typeof <dominio>Schema>;
export type Create<Dominio>Validated = z.infer<typeof create<Dominio>Schema>;
export type Update<Dominio>Validated = z.infer<typeof update<Dominio>Schema>;

export function validateCreate<Dominio>(data: unknown) {
  return create<Dominio>Schema.safeParse(data);
}

export function validateUpdate<Dominio>(data: unknown) {
  return update<Dominio>Schema.safeParse(data);
}

`hooks/use--query.ts`

import { useQuery } from '@tanstack/react-query';
import { queryKeys } from '@/shared/lib';
import { <dominio>Api } from '../api';

export function useAll<Dominio>s() {
  const query = useQuery({
    queryKey: queryKeys.<dominios>.list(),
    queryFn: () => <dominio>Api.getAll(),
  });

  return {
    <dominios>: query.data?.data ?? null,
    is<Dominio>sLoading: query.isLoading,
    error: query.error,
  };
}
```

Adicionar grupo em `src/shared/lib/query-keys.ts` (`queryKeys..all` / `.list()` / `.detail(id)`) — nunca arrays inline.

`hooks/use--mutation.ts`

import { useMutation, useQueryClient } from '@tanstack/react-query';
import { queryKeys } from '@/shared/lib';
import { <dominio>Api } from '../api';
import type { Create<Dominio>Data, Update<Dominio>Data } from '../types';

export function useCreate<Dominio>() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: (data: Create<Dominio>Data) => <dominio>Api.create(data),
    onSuccess: () =>
      queryClient.invalidateQueries({ queryKey: queryKeys.<dominios>.all }),
    meta: { globalErrorToast: true },
  });
}

Critérios de qualidade

  • Todos os arquivos canônicos (`api/{client,endpoints,index}`, `hooks/{query,mutation,index}`, `types.ts`, `validators.ts`, `index.ts`) presentes. **Sem `service.ts`.**
  • `types.ts` tem ``, `CreateData`, `UpdateData` — não inventar campos sem confirmação.
  • `validators.ts` reusa `shared/lib/fields/` quando o campo já é coberto (cpf, email, etc.).
  • Catálogo validado contra schema.
  • Nenhum `any` no código gerado.
  • Imports usando alias `@/`.

Confiança / rastreabilidade

OrigemConfiança
Estrutura espelhando `web-template/src/features/tasks/`alta
Campos do tipo `` quando confirmados pelo usuárioalta
Campos quando inferidos (não confirmados)baixa — não gerar sem confirmar
Mapeamento de endpoint quando o usuário forneceu listaalta
Mapeamento de endpoint inferido (CRUD padrão)média

Você NUNCA

  • Cria feature sem confirmar microsserviço e shape do tipo com o usuário.
  • Gera `service.ts` (classe `Service` estática) — não faz parte do contrato do template atual.
  • Inventa campos do domínio (CPF, valor, data) por suposição.
  • Cria componente de UI dentro da feature na etapa de scaffold — isso é FE-03/FE-04.
  • Sobrescreve feature existente — se o usuário pediu e a feature existe, perguntar se é refator ou novo nome.
  • Pula a etapa de atualizar o catálogo.

Você SEMPRE

  • Espelha o padrão de `web-template/src/features/tasks/` arquivo por arquivo.
  • Adiciona `enabled: !!id` em queries que dependem de parâmetro.
  • Invalida queries certas em cada mutation (`all` no create/delete; `all` + `byId` no update).
  • Linka `linked_screens: [SC-NN]` no catálogo quando o usuário cita o ID de tela do FG-02.
