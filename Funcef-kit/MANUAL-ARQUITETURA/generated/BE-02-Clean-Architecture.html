BE-02 — Clean Architecture

2.1 Visão macro

Todo microserviço FUNCEF segue Clean Architecture em 4 camadas. As dependências apontam para dentro (em direção ao Domain). Nenhuma camada interna conhece as camadas externas.

graph TB
    subgraph Outer ["Camada externa"]
        API["{Servico}.API<br/>(Controllers, Program.cs)"]
        Tests["{Servico}.Tests"]
    end

    subgraph Middle ["Camada intermediária"]
        App["{Servico}.Application<br/>(Commands, Queries, Handlers,<br/>Services, Validators, DTOs)"]
        Infra["{Servico}.Infrastructure<br/>(AppDbContext, Seeders, DI)"]
    end

    subgraph Inner ["Camada central"]
        Domain["{Servico}.Domain<br/>(Entidades)"]
    end

    API --> App
    API --> Infra
    App --> Domain
    Infra --> Domain
    Infra --> App
    Tests --> API
    Tests --> App
    Tests --> Domain
    Tests --> Infra
```

Aviso **Convenção crítica**

A camada `Application` **NÃO** referencia `Infrastructure`. Quem amarra as duas é o `Program.cs` (camada API) via `AddApplicationServices()` + `AddInfrastructureServices()`.

2.4 Responsabilidades por camada

Domain — `{Servico}.Domain`

Responsável porNÃO faz
Entidades de negócio (cada uma com **PK própria**, sem classe base compartilhada)Acesso a banco, HTTP, DI, lógica de aplicação
Mapeamento Oracle via Data Annotations (`[Table]`, `[Column]`, `[Index]`, `[ForeignKey]`)Fluent API (vai no `AppDbContext`)
Atributos de auditoria (`[Auditable]`) e auto-include (`[AutoInclude]`)Repositórios, services
Invariantes simples (`[Required]`, `[Range]`, `[MaxLength]`, `[EmailAddress]`)Regras de domínio ricas com I/O (vão no Service). Motores de domínio puros, sem I/O (ex.: avaliador de decisão do GAP), são aceitáveis no Domain

Único pacote NuGet usado: `FUNCEF.ORM` (para os atributos). **Não depende** de EF Core diretamente.

**PK — surrogate `long` Identity, nomeada por entidade (alinhada ao BancoDados).** Não há `BaseEntity` compartilhado: um `[Column("ID")]` herdado fixaria o nome da PK para todas as tabelas e violaria a convenção BancoDados (ADR-014/015: PK = `{ENTIDADE}_ID`, FK com o mesmo nome). Cada entidade declara a própria chave:

[Table("TB_SISTEMAS", Schema = "GAP")]
[Auditable("Sistema")]
public class Sistema
{
    [Key]
    [Column("SISTEMA_ID")]
    [DatabaseGenerated(DatabaseGeneratedOption.Identity)]
    public long Id { get; set; }
    // ... demais colunas
}
```

**Nota Oracle:** o padrão FUNCEF de PK é **`NUMBER` surrogate com `IDENTITY`** (`DatabaseGeneratedOption.Identity`) — o banco gera o valor no insert; a aplicação **não** seta o `Id`. A coluna da PK segue a nomenclatura BancoDados `{ENTIDADE}_ID` (não um `ID` genérico). FK usa exatamente o mesmo nome da PK referenciada. Ver [BE-04](../persistencia/BE-04-Persistencia-Transacoes.md) §4.4 e a doutrina BancoDados (BD-04, ADR-014/015).

Application — `{Servico}.Application`

Responsável porNÃO faz
**Commands** (`ICommand`): intenção de mudança de estadoPersistência direta
**Queries** (`IQuery`): leituraLógica de negócio espalhada nos controllers
**Handlers**: orquestram o caso de uso. Em Commands controlam transação (`IUnitOfWork`); em Queries só leem.Validação manual de entrada (delegada ao pipeline `ValidationBehavior`)
**Services**: regras de negócio e acesso a dados via `IRepository`Controle de transação (responsabilidade do Handler)
**Validators**: `AbstractValidator` — só Commands têm validatorsValidar Queries (validadas no próprio Handler quando necessário)
**DTOs**: Request (entrada), Response (saída completa), Resume (saída resumida para listagens)DTOs sem `[MapFrom]`/`[NestedMap]`
**Exceptions**: (opcional) extensões locais de `BusinessException` para conflitos de domínio próprios — `NotFoundException`/`BusinessException`/`ValidationException`/`ConflictException` já vêm de `FUNCEF.Essenciais`Try/catch espalhado
`ServiceCollectionExtensions.AddApplicationServices()`Registrar serviços de infraestrutura

Infrastructure — `{Servico}.Infrastructure`

Responsável porNÃO faz
`AppDbContext : BaseDbContext` — DbSets e Fluent API avançada (índices compostos, unique filtrados, `OnDelete`)Entidades (ficam no Domain)
Seeders (`EntitySeederBase`) executados em Dev via `AddFuncefORMDevelopment`Seeders de produção
Registro de **toda** a stack externa via `ServiceCollectionExtensions`: Key Vault, ORM, NoSQL (cache/documentos), Auth (inclui auditoria de acesso em Oracle), Storage, TelemetriaLógica de negócio
`ConfigurationValidationExtensions` — fail-fast em produção (`ValidateOnStart`)Validação em dev/hml (mais flexível)

API — `{Servico}.API`

Responsável porNÃO faz
`Program.cs`: pipeline HTTP, CORS, sessão, rate limiting, health, Swagger, exception handlerLógica de negócio
Controllers herdando de `BaseController` (FuncefEssenciais), recebendo `IMediator` + `ITelemetry`Acesso direto a `AppDbContext` ou repositórios
Mapeamento HTTP→Command/Query (controller fino)Validação manual (pipeline cuida)
Configuração JSON: CamelCase, ignore null, enum como string—

2.5 Fluxo de uma requisição (sequência canônica)

Sequência genérica para um POST `/{Entidades}` que cria recurso:

sequenceDiagram
    autonumber
    participant Cli as Cliente HTTP
    participant Ctrl as {Entidades}Controller
    participant Med as IMediator
    participant Val as ValidationBehavior
    participant Vdr as Create{Entidade}Validator
    participant Hnd as Create{Entidade}Handler
    participant Svc as {Entidade}Service
    participant Rep as IRepository<{Entidade}>
    participant UoW as IUnitOfWork
    participant Db as Oracle

    Cli->>Ctrl: POST /{Entidades} (Bearer JWT)
    Ctrl->>Med: Send(Create{Entidade}Command)
    Med->>Val: pipeline
    Val->>Vdr: ValidateAsync(command)
    alt Erros
        Vdr-->>Val: failures
        Val-->>Ctrl: ValidationException (400)
        Ctrl-->>Cli: HTTP 400 (GlobalExceptionMiddleware)
    else OK
        Val->>Hnd: Handle(command)
        Hnd->>Svc: CreateAsync(request)
        Svc->>Rep: ExistsAsync(predicate)
        Rep->>Db: SELECT 1 FROM {TABELA} WHERE …
        alt Conflito (unicidade)
            Svc-->>Hnd: throw ConflictException
            Hnd-->>Med: bubble up
            Med-->>Ctrl: ConflictException
            Ctrl-->>Cli: HTTP 409
        else Disponível
            Svc->>Rep: AddAsync(entity)
            Svc-->>Hnd: entity
            Hnd->>UoW: SaveChangesAsync()
            UoW->>Db: INSERT {TABELA}
            Hnd->>Hnd: entity.MapTo<…,Response>()
            Hnd-->>Ctrl: {Entidade}Response
            Ctrl-->>Cli: HTTP 201 Created
        end
    end
```

A ordem dos middlewares é **fixa** (justificativa em [Decisoes-Arquiteturais](../_shared/Decisoes-Arquiteturais.md) ADR-013):

WebApplication.CreateBuilder

2.7 Dependency Injection — onde cada coisa é registrada

OndeO que é registrado
`{Servico}.Application/Extensions/ServiceCollectionExtensions.cs``AddMediatorWithDefaults(this assembly)` (escaneia handlers, validators, behaviors) + `AddScoped` para cada Service
`{Servico}.Infrastructure/Extensions/ServiceCollectionExtensions.cs`Key Vault, Telemetria (Azure Monitor ou Console), `FUNCEF.ORM` + `AppDbContext` + `IUnitOfWork`, cache/documentos NoSQL (`AddRedisCache` / `AddMongoDocuments`, conn string via Key Vault), `FUNCEF.ORM.Audit`, `AddFUNCEFAuthentication` (já inclui auditoria de acesso em Oracle via `IAccessAuditService` e Redis via `FUNCEF.NoSql`/`ICacheStore`), Azure Storage, Object Mapper

2.8 Handler × Service — a separação de responsabilidades

A separação Handler/Service é uma escolha consciente da equipe (não está no padrão CQRS clássico). Aparece em **todos** os casos de uso:

graph LR
    H["Handler<br/>(orquestra)"] -->|"chama lógica"| S["Service<br/>(regras + dados)"]
    H -->|"controla transação"| U["IUnitOfWork<br/>(SaveChanges,<br/>Begin/Commit/Rollback)"]
    S -->|"persistência"| R["IRepository&lt;T&gt;<br/>(Add/Update/Delete/<br/>GetById/GetPaged)"]
```
ComponenteResponsabilidadeInjeta
**Handler**Orquestra o caso de uso. Faz `Begin/Commit/Rollback` quando precisa. Faz `MapTo<…>` para DTO. Loga via `ITelemetry`.`I{Entidade}Service`, `IUnitOfWork`, `ITelemetry` (opcional)
**Service**Validações de negócio (unicidade, existência, integridade referencial). Acesso a dados via `IRepository`. Lança exceções tipadas.`IRepository` (uma ou mais)

Padrão de Handler (placeholder):

public class Create{Entidade}Handler : ICommandHandler<Create{Entidade}Command, {Entidade}Response>
{
    private readonly I{Entidade}Service _service;
    private readonly IUnitOfWork _unitOfWork;

    public Create{Entidade}Handler(I{Entidade}Service service, IUnitOfWork unitOfWork)
    {
        _service = service;
        _unitOfWork = unitOfWork;
    }

    public async Task<{Entidade}Response> Handle(Create{Entidade}Command command, CancellationToken ct)
    {
        var entity = await _service.CreateAsync(command.Request, ct);
        await _unitOfWork.SaveChangesAsync(ct);
        return entity.MapTo<Domain.Entities.{Entidade}, {Entidade}Response>();
    }
}
```

Padrão de Service com regra de negócio + exceção tipada:

public virtual async Task<{Entidade}> CreateAsync({Entidade}Request request, CancellationToken ct = default)
{
    if (await _repository.ExistsAsync(e => e.CampoUnico == request.CampoUnico, cancellationToken: ct))
        throw new ConflictException("{Entidade}", "Já existe um registro com este {campo}");

    var entity = request.MapTo<{Entidade}Request, {Entidade}>(e =>
    {
        // Id NÃO é setado: a PK é IDENTITY, gerada pelo banco no insert.
        e.DataCriacao = DateTime.UtcNow;
    });

    await _repository.AddAsync(entity, ct);
    return entity;
}
```

2.9 Benefícios e tradeoffs do desenho

BenefícioComo aparece
Testabilidade altaHandlers e Services testados sem banco real, via `Substitute.For>()`
Trocar EF Core por Dapper sem mudar HandlerHandler chama método do Service; só a implementação do Service muda
Domain livre de frameworkEntidades dependem só de Data Annotations padrão do .NET + atributos do `FUNCEF.ORM`
Validação isolada do controllerController nunca tem `if (!request.IsValid) return BadRequest()`
Reutilização de Services entre HandlersHandler de transação combinada pode chamar `I{Entidade1}Service` + `I{Entidade2}Service`
TradeoffMitigação
Mais arquivos por feature (Command + Handler + Validator + Service + DTOs)Convenção rígida de nome/pasta torna previsível; Scrutor registra Handlers e Validators automaticamente
Service é "extra" comparado a CQRS clássicoReutilização entre Handlers e separação clara transação ↔ regra justifica o custo
