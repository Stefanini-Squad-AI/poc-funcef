Padrões Arquiteturais — Frontend FUNCEF

Nota **Fonte autoritativa**

`funcef/web-template/ARCHITECTURE.md` e código em `src/`. Este documento condensa os padrões em formato útil para agentes IA.

Visão geral em uma frase

**Feature-Based + Colocation**: a aplicação é fatiada por funcionalidade do usuário (`features/`), cada uma auto-contida; componentes de página ficam ao lado da rota (`_components/`); o que é genuinamente compartilhado vive em `shared/`; infra transversal em `core/`.

Camadas e regra de dependência (4 camadas)

O `web-template` v3.4.0 organiza `src/` em **4 camadas**. A camada `core/` concentra **infra transversal**: `api`, `auth`, `config`. Estado global (Zustand) **não é camada** — adicionar sob demanda.

+-----------------------------------------------------+
|  app/                  (Next.js App Router)         |  ← topo; importa feature/core/shared
|    (authenticated)/                                 |
|    <rota>/page.tsx                                  |
|    <rota>/_components/                              |
|    api/bff/[...path]/route.ts   (BFF único)         |
+-----------------------------------------------------+
                ↓ importa
+-----------------------------------------------------+
|  features/<dominio>/   (lógica de negócio)          |
|    api/{client,endpoints,index}  hooks/  components/|
|    types.ts  validators.ts  index.ts   (SEM service)|
+-----------------------------------------------------+
                ↓ importa
+-----------------------------------------------------+
|  core/                 (infra transversal)          |
|    api.ts  auth/  config/                           |
+-----------------------------------------------------+
                ↓ importa
+-----------------------------------------------------+
|  shared/               (utilitários e UI base)      |
|    ui/  lib/  hooks/  types/  config/               |
+-----------------------------------------------------+
```

Fora das camadas: arquivos na raiz de `src/` (`proxy.ts`, `instrumentation.ts`) — tratados como `app` pelo lint.

**Regra de dependência (exatamente o que o lint aplica):**

DePode importar
`app``app`, `feature`, `core`, `shared`
`feature`**a MESMA feature** (não outra), `core`, `shared`
`core``core`, `shared`
`shared`**só** `shared`

[!IMPORTANT]

**Boundaries são guardrail duro, não convenção textual**

A regra acima é **enforçada por `eslint-plugin-boundaries` (`^7.2.0`)** em `eslint.config.mjs` (`default: 'disallow'` + regra explícita por camada; `feature` usa `capture: ['feature']` para permitir apenas imports **dentro da mesma feature**). Import que cruze a fronteira **falha o lint** (não é só recomendação). Ao mover/renomear código, este é o mecanismo canônico de verificação — não a leitura manual do diagrama.

Estrutura canônica de uma feature (SEM `service.ts`)

Estrutura observada em `web-template/src/features/tasks/`. **Não existe `service.ts`** — os hooks (React Query) chamam a instância `api` de `@/core/api` direto, via `api/client.ts`:

features/<dominio>/
├── api/
│   ├── client.ts        ← objeto tipado que chama api<T> (tasksApi.getAll(), .create(), ...)
│   ├── endpoints.ts     ← builders puros — retornam paths, sem HTTP
│   └── index.ts         ← barrel
├── hooks/
│   ├── use-<dominio>-query.ts     ← useQuery → chama <dominio>Api.*
│   ├── use-<dominio>-mutation.ts  ← useMutation + invalidateQueries
│   └── index.ts
├── components/          ← UI do domínio (quando reutilizada entre rotas)
├── types.ts             ← tipos do domínio (Task, CreateTaskData)
├── validators.ts        ← schemas Zod (somente quando há formulários)
└── index.ts             ← barrel
```

**Fluxo dentro da feature:** `components → hooks (React Query) → api/{client,endpoints} → api (@/core/api) → types/validators`. Regra de negócio/orquestração/transformação vive **no hook** (ou num util de `shared/lib`), não numa classe estática intermediária.

Padrão de `api/client.ts`

import { api } from '@/core/api';
import { endpoints } from './endpoints';
import type { CreateTaskData, Task } from '../types';

export const tasksApi = {
  getAll: () => api.get<Task[]>(endpoints.list()),
  create: (data: CreateTaskData) =>
    api.post<Task, CreateTaskData>(endpoints.create(), data),
};
```

`api` (de `@/core/api`, `createApi` da lib) é o **cliente único same-origin** — envelope FUNCEF normalizado, erro carimbado e `401 → teardown`. Não instanciar HTTP client na feature.

Padrão de `types.ts`

export type Task = {
  id: number;
  title: string;
  completed: boolean;
};

export type CreateTaskData = Omit<Task, 'id'>;
```

Padrão de `validators.ts`

import { z } from 'zod';

export const taskSchema = z.object({
  id: z.number().int().positive(),
  title: z.string().min(1).max(200).trim(),
  completed: z.boolean(),
});

export const createTaskSchema = taskSchema.omit({ id: true });

export type TaskValidated = z.infer<typeof taskSchema>;
export type CreateTaskValidated = z.infer<typeof createTaskSchema>;
```

Fluxo de dados (mutation típica) — BFF único same-origin

O padrão canônico de dados é **BFF (Backend-for-Frontend) same-origin**: o browser fala **apenas** com `/api/bff/*` (rota `app/api/bff/[...path]/route.ts`). O access token (Bearer) é resolvido **no servidor** (`createBffHandler` + `createFuncefAuth`) e anexado ao upstream (`API_URL`) — **nunca** exposto ao JavaScript do browser. O browser só envia o cookie de sessão httpOnly.

User clica "Salvar"
    ↓
Componente em app/<rota>/_components/
    ↓ chama
useCreateTask().mutateAsync(data)              ← hook React Query (features/tasks/hooks)
    ↓
tasksApi.create(data)                          ← features/tasks/api/client.ts
    ↓
api.post<Task>(endpoints.create(), data)       ← api (@/core/api — createApi da lib)
    ↓  baseURL = ${APP_URL}${BASE_PATH}/api/bff
BFF route handler: app/api/bff/[...path]/route.ts
    ↓  resolve Bearer server-side e encaminha para API_URL
Backend (microsserviço / mock json-server)
    ↓ resposta (envelope normalizado pela lib)
React Query Cache → invalidateQueries(queryKeys.tasks.all)
    ↓
UI re-renderiza (query refetched)
```

[!NOTE]

**`createApi` não injeta Bearer no browser**

No modelo BFF o `Authorization` é anexado **no route handler** (server). O token nunca transita pelo cliente. Query keys sempre pela factory central `queryKeys` (`src/shared/lib/query-keys.ts`).

Camadas de validação (Zod)

shared/lib/validators/         ← funções puras (Business Logic)
  cpf-validation.ts (isCpfValid, cleanCpf)
  password-validation.ts
        ↓ usadas por
shared/lib/fields/              ← Zod schemas atômicos reutilizáveis
  cpf-field.ts (cpfField)
  email-field.ts (emailField)
        ↓ usados por
features/<X>/validators.ts      ← schemas compostos (taskSchema)
        ↓ usado por
zodResolver(schema) em React Hook Form
```

`shared/lib/formatters/` (CPF, moeda, data) **consome** `validators/` — nunca duplica lógica.

Organização de componentes — 3 lugares válidos

graph TB
    A[Componente que vou criar] --> B{Onde colocar?}
    B -->|Reusável em múltiplas páginas/features<br/>e não existe na lib| C["shared/ui/&lt;componente&gt;/"]
    B -->|Específico de UMA rota| D["app/.../&lt;rota&gt;/_components/&lt;componente&gt;/"]
    B -->|Específico de UMA feature, usado por múltiplas rotas| E["features/&lt;X&gt;/components/&lt;componente&gt;/"]
    B -->|"Já existe na @funcef-componentes/react"| F["NÃO criar — usar a lib"]

    style C fill:#e8f5e9
    style D fill:#fff4e1
    style E fill:#e1f5ff
    style F fill:#ffcccc
```

**Decisão em árvore**:

  1. A lib `@funcef-componentes/react` já tem? → **usa a lib**.
  2. A lib quase tem mas falta uma variante? → **abre issue no lib-front-ui**, não duplica.
  3. É genuinamente novo e usado em **mais de uma rota**? → `shared/ui/`.
  4. É de **uma feature** mas reutilizado em rotas diferentes? → `features//components/`.
  5. É de **uma rota específica**? → `app/.../_components/`.

Estado global (Zustand) — sob demanda

O template v3.4.0 **não inclui** Zustand nem pasta `store/`. Adicionar apenas quando:

  • Estado é **cross-componente / cross-rota** (preferências de UI, wizard multi-step).
  • **Não** é estado de servidor (React Query) nem local de componente (`useState`/RHF).

Quando adotado, seguir padrão de slices documentado em FE-05 — fora do grafo de camadas do lint.

Configuração de HTTP — `core/api.ts`

**Padrão canônico:** instância única `api` em `src/core/api.ts`:

import { createApi } from '@funcef-componentes/auth/http';
import { envClient } from '@/shared/config/env-client';

export const api = createApi({
  baseURL: `${envClient.APP_URL}${envClient.BASE_PATH}/api/bff`,
});
```
  • BFF: `app/api/bff/[...path]/route.ts` com `createBffHandler(auth, { upstreamUrl: env.API_URL })`.
  • `API_URL` é **server-only** (Zod em `shared/config/env.ts` + `import 'server-only'`).
  • Envelope FUNCEF, retry seletivo e toasts vêm da lib — não reimplementar por feature.

[!WARNING]

**Chamada direta ao backend no browser é EXCEÇÃO**

Bypass do BFF reexpõe o token ao JS. Registrar exceção em [Excecoes-Aprovadas](./Excecoes-Aprovadas.md) e justificar.

Convenções de import

// 1. React e externos
import React from 'react';

Roteamento (Next App Router)

app/
├── layout.tsx                ← layout raiz (html, body, providers globais)
├── (authenticated)/          ← route group autenticado
│   ├── layout.tsx            ← AppShell + getServerSession
│   ├── tasks/
│   │   ├── page.tsx          ← lista
│   │   └── _components/      ← task-list, create-task-form (locais)
│   └── ...
├── api/
│   ├── auth/[...all]/route.ts
│   └── bff/[...path]/route.ts
└── sign-in/
    └── page.tsx
```
  • **`(group)`** = route group (não vira segmento de URL).
  • **`_components/`** com underscore = pasta privada (não vira rota).
  • **`page.tsx`** vira a rota; **`layout.tsx`** envolve todas as páginas abaixo.

Boas práticas resumidas

#Regra
1Uma feature por domínio. Não misturar `tasks` com `pedidos`.
2Estado de servidor → React Query. Estado de UI cross-componente → Zustand (opt-in). Estado local → `useState`.
3Componente sem estado é melhor — extrair lógica para hook.
4`forwardRef` quando o componente renderiza HTML primitivo. Sempre setar `displayName`.
5Sem `console.log` em produção (lint avisa). Usar logger se necessário.
6Sem `any` casual — preferir `unknown` + narrowing.
7Toda mutation invalida queries relacionadas via `queryKeys` factory.
8Toda chamada HTTP do browser passa por `api` (`@/core/api`) → BFF `/api/bff` — nada de `fetch()` solto nem client HTTP ad hoc (exceção documentada à parte).
9Tailwind: classes inline; composição via `cn()`. Sem CSS Module a não ser exceção justificada.
10Imports relativos só dentro da mesma pasta (`./` ok, `../../` proibido — usar alias `@/`).
