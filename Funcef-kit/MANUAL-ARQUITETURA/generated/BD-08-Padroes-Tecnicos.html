8.1 Substituição de BOOLEAN (PDF §8.1)

Aviso **Regra inflexível**

**Não utilizar o tipo `BOOLEAN`** devido a limitações de compatibilidade entre plataformas (Oracle 19c não tem `BOOLEAN` em DDL de tabela).

Importante **Padrão de boolean = `NUMBER(1) 0/1` ([ADR-017](../_shared/Decisoes-Arquiteturais.md), 2026-07-08)**

Desde 2026-07-08 o padrão para objeto **novo/alterado** é `NUMBER(1) NOT NULL CHECK IN (0,1)`. A forma anterior `CHAR(1) IN ('S','N')` (ADR-002) foi **revertida**; colunas legadas `'S'/'N'` permanecem válidas (**forward-only**) até eventual migração sob governança do DBA.

Padrão FUNCEF

Representar valores binários com:

<COLUNA> NUMBER(1) NOT NULL,
CONSTRAINT CK_<TABELA>_<COLUNA> CHECK (<COLUNA> IN (0,1))
```
  • **Tipo:** `NUMBER(1)`.
  • **Constraint:** `NOT NULL` (não permite ambiguidade NULL).
  • **Domínio:** `1` (sim/true) e `0` (não/false).
  • **Nome:** convenção FUNCEF — `FLAG_` (ex.: `FLAG_ATIVO`, `FLAG_BLOQUEADO`, `FLAG_VINCULADO`).

[!WARNING]

**Nunca misturar `'S'`/`'N'` com `NUMBER(1)`**

Toda expressão derivada da flag (CK compostas, índices filtrados, views, COMMENTs) usa os literais **numéricos** `0`/`1`. Comparar `FLAG_ATIVO = 'S'` numa coluna `NUMBER(1)` gera **`ORA-01722` (invalid number)** e quebra a criação do objeto.

[!IMPORTANT]

**`FLAG_`, não `IND_`**

Flag booleana usa prefixo `FLAG_` (não `IND_`); `IND_` fica reservado a indicadores de negócio não-booleanos (ex.: `IND_RISCO`). Reconcilia a contradição com a lista de [Abreviacoes-Padronizadas](../_shared/Abreviacoes-Padronizadas.md).

Exemplo completo

CREATE TABLE CAD.TB_CLIENTES (
    CLIENTE_ID       NUMBER GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    NOME_CLIENTE     VARCHAR2(100 CHAR) NOT NULL,
    FLAG_ATIVO       NUMBER(1) NOT NULL,
    FLAG_BLOQUEADO   NUMBER(1) NOT NULL,
    FLAG_AUTORIZADO  NUMBER(1) NOT NULL,
    CONSTRAINT PK_CLIENTES PRIMARY KEY (CLIENTE_ID),
    CONSTRAINT CK_CLIENTES_FLAG_ATIVO       CHECK (FLAG_ATIVO IN (0,1)),
    CONSTRAINT CK_CLIENTES_FLAG_BLOQUEADO   CHECK (FLAG_BLOQUEADO IN (0,1)),
    CONSTRAINT CK_CLIENTES_FLAG_AUTORIZADO  CHECK (FLAG_AUTORIZADO IN (0,1))
);
```

Mapeamento no .NET (EF Core)

Em microserviços .NET, mapear `bool` ↔ `NUMBER(1)`:

[Column("FLAG_ATIVO", TypeName = "NUMBER(1)")]
public bool FlagAtivo { get; set; }
```

Nota **Sem conversor**

O provider Oracle do EF Core já mapeia `bool` ↔ `NUMBER(1)` (`true→1`, `false→0`) nativamente — **não é necessário** `HasConversion`. Se por algum motivo precisar ser explícito:

modelBuilder.Entity<Cliente>()
    .Property(e => e.FlagAtivo)
    .HasConversion(v => v ? 1 : 0, v => v == 1);

Para colunas **legadas** ainda em `CHAR(1) 'S'/'N'` (forward-only), mantenha o conversor `v => v ? "S" : "N"` com `TypeName = "CHAR(1)"`.

Detalhes em [Aplicando-em-Microservico-NET](../guias/Aplicando-em-Microservico-NET.md) §3.

Decisão registrada

[Decisoes-Arquiteturais](../_shared/Decisoes-Arquiteturais.md) **ADR-017** (supersede **ADR-002**) — `NUMBER(1) + CHECK IN (0,1)` como boolean padrão; `BOOLEAN` continua proibido (Oracle 19c). Legado `CHAR(1) 'S'/'N'` permanece válido (forward-only).

8.2 Controle de alteração — `DATA_INCLUSAO_ALTERACAO` (PDF §8.2)

[!IMPORTANT]

**Regra (ADR-016 — estende ADR-005 e o PDF §8.2)**

**Toda tabela nova recebe `DATA_INCLUSAO_ALTERACAO` por padrão** — ela é o carimbo de controle de **carga incremental, sincronização entre sistemas e auditoria leve**. A **omissão é a exceção** (não o contrário): só se justifica para tabela comprovadamente sem participação em carga incremental/auditoria (ex.: domínio puramente estático), e **exige exceção registrada** em [Excecoes-Aprovadas](../_shared/Excecoes-Aprovadas.md).

Especificação

AspectoValor
**Nome exato**`DATA_INCLUSAO_ALTERACAO`
**Tipo**`DATE`
**NOT NULL****Sim** (padrão)
**Presença****Padrão em toda tabela nova** (omitir só com exceção justificada)
**Mantida por****Aplicação** (não trigger, salvo exceção justificada)

Diretrizes de uso (ADR-016 — default em todas; a matriz do PDF §8.2 vira ordem de prioridade, não permissão para omitir)

Categoria de tabelaInclusão da coluna
**Tabela transacional****Obrigatória**
**Tabela usada em sincronização entre sistemas****Obrigatória**
**Tabela associativa** (frequente ou rara)**Incluir por padrão**
**Tabela de domínio / lookup****Incluir por padrão** — omitir só se puramente estática, com exceção justificada registrada
**Tabela que não participa de carga incremental****Incluir por padrão** (serve à auditoria leve); omitir só com exceção justificada

Exceção (ADR-016)

A coluna é **default**. Para **omiti-la**, a tabela precisa ser comprovadamente estática/sem carga incremental **e** a omissão deve ser registrada como exceção justificada em [Excecoes-Aprovadas](../_shared/Excecoes-Aprovadas.md).

Exemplo

CREATE TABLE CAD.TB_CLIENTES (
    CLIENTE_ID              NUMBER GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    CPF                     VARCHAR2(11 CHAR) NOT NULL,
    NOME_CLIENTE            VARCHAR2(100 CHAR) NOT NULL,
    FLAG_ATIVO              NUMBER(1) NOT NULL,
    DATA_INCLUSAO_ALTERACAO DATE NOT NULL,
    CONSTRAINT PK_CLIENTES PRIMARY KEY (CLIENTE_ID),
    CONSTRAINT UK_CLIENTES_CPF UNIQUE (CPF),
    CONSTRAINT CK_CLIENTES_FLAG_ATIVO CHECK (FLAG_ATIVO IN (0,1))
);
```

Quem atualiza

[!NOTE]

**Aplicação mantém a coluna**

A regra "mantida pela aplicação" significa:

  1. No **INSERT**, a aplicação seta `DATA_INCLUSAO_ALTERACAO = SYSDATE` (ou equivalente no .NET — `DateTime.UtcNow`/`DateTime.Now`).
  2. No **UPDATE**, a aplicação **sempre** atualiza para `SYSDATE` (mesmo que nenhuma outra coluna mude logicamente).

Não é trigger porque:

  • A aplicação sabe o momento certo (commit transacional).
  • Trigger esconde comportamento e dificulta debug.
  • Trigger gera overhead em batch.

Microsserviços .NET

Implementação típica:

public abstract class BaseEntity
{
    [Column("DATA_INCLUSAO_ALTERACAO")]
    public DateTime DataInclusaoAlteracao { get; set; }
}

// Override do SaveChanges no AppDbContext:
public override int SaveChanges()
{
    var entries = ChangeTracker.Entries<BaseEntity>()
        .Where(e => e.State == EntityState.Added || e.State == EntityState.Modified);
    foreach (var e in entries)
        e.Entity.DataInclusaoAlteracao = DateTime.UtcNow;
    return base.SaveChanges();
}
```

[!NOTE]

**FuncefORM cobre isso?**

Verifique no projeto — `BaseEntity` ou interceptor próprio do `FUNCEF.ORM` pode já popular a coluna. Caso contrário, implementar no `AppDbContext` do serviço.

Decisão registrada

[Decisoes-Arquiteturais](../_shared/Decisoes-Arquiteturais.md) **ADR-005** (coluna obrigatória) + **ADR-016** (obrigatória por padrão em **toda** tabela nova; omissão só com exceção justificada).

8.3 Outros padrões técnicos correlatos

Estes pontos não estão explicitamente em §8 do PDF mas decorrem dos princípios gerais e são tratados em outros capítulos:

8.3.1 Surrogate key obrigatória

AspectoPadrão

**NOT NULL**Sim

8.3.2 Tipos canônicos

Vide [Stack-Canonica](../../backend/_shared/Stack-Canonica.md) §Tipos canônicos Oracle.

Resumo:

ConceitoTipo
Identificador`NUMBER GENERATED BY DEFAULT AS IDENTITY`
Inteiro`NUMBER(10)`
Decimal monetário`NUMBER(15,2)`
Decimal percentual`NUMBER(5,2)`
Texto`VARCHAR2(N CHAR)` (sempre `CHAR`, nunca `BYTE`)
Texto grande`CLOB` (apenas se > 4000 char)

Data + timezone`TIMESTAMP WITH TIME ZONE`
Binário`NUMBER(1) + CHECK IN (0,1)` (ADR-017; legado `CHAR(1) 'S'/'N'` mantido)
GUID`RAW(16)`
Blob grande`BLOB` (preferir Azure Blob)

8.3.3 Charset

Schema com **AL32UTF8** — sempre declarar `VARCHAR2(N CHAR)` para suportar UTF-8 sem ambiguidade de bytes.

8.3.4 Default values

CasoPadrão
Datas de inclusão`DEFAULT SYSDATE` (em LOG/HIST se aplicação não controla)
FlagsSem `DEFAULT` — aplicação seta explicitamente para evitar "default escondido"
Sequences`GENERATED BY DEFAULT AS IDENTITY`

[!NOTE]

**Cuidado com defaults**

`DEFAULT` em coluna `NOT NULL` esconde lógica. Prefira que a aplicação seja explícita. Use `DEFAULT` apenas para `SYSDATE` em LOG/HIST e para flags claramente padronizados.

8.3.5 Row Level Security (VPD) — controle de acesso por linha

Para tabelas que misturam linhas de donos/segmentos diferentes e precisam de filtro **garantido pelo banco** (multi-tenant na mesma tabela, segregação por participante/unidade, defesa em profundidade para dado sensível), usar **Oracle VPD (Virtual Private Database / RLS)**. O banco anexa um predicado `WHERE` a todo `SELECT/UPDATE/DELETE`, de forma transparente. Decisão de **usar** RLS e sua governança em [BD-10-Qualidade-Governanca](../governanca/BD-10-Qualidade-Governanca.md) §10.4.

[!IMPORTANT]

**A policy é do DBA (PROD exige DBA)**

`DBMS_RLS.ADD_POLICY` é executado pelo **DBA**, não pela aplicação nem pela IA. A IA pode **propor o script** (função de predicado + policy) para revisão; nunca aplicar em PROD.

**1) Função de predicado** — retorna o `WHERE` dinâmico a partir de um *application context*:

CREATE OR REPLACE FUNCTION CAD.FN_RLS_CLIENTES (
    P_SCHEMA IN VARCHAR2,
    P_OBJETO IN VARCHAR2
) RETURN VARCHAR2
AS
BEGIN
    -- Isenta jobs/relatórios (usuário de serviço de ETL/BI)
    IF SYS_CONTEXT('USERENV','SESSION_USER') = 'CAD_ETL' THEN
        RETURN '1=1';
    END IF;
    -- Filtra pela unidade do contexto da requisição (setado pela aplicação)
    RETURN 'UNIDADE_ID = SYS_CONTEXT(''CTX_FUNCEF'',''UNIDADE_ID'')';
END;
```

**2) Policy** (DBA):

BEGIN
    DBMS_RLS.ADD_POLICY(
        object_schema   => 'CAD',
        object_name     => 'TB_CLIENTES',
        policy_name     => 'RLS_CLIENTES_UNIDADE',
        function_schema => 'CAD',
        policy_function => 'FN_RLS_CLIENTES',
        statement_types => 'SELECT,UPDATE,DELETE',
        update_check    => TRUE);   -- impede gravar linha que sairia do filtro
END;
```

**3) Application context** — `SELECT` não carrega o usuário final (pool usa um único schema user). A aplicação **seta o contexto por requisição** via um package que só o app pode chamar:

CREATE CONTEXT CTX_FUNCEF USING CAD.PKG_CTX_FUNCEF;   -- DBA cria o contexto
-- PKG_CTX_FUNCEF.set_unidade(p) chama DBMS_SESSION.SET_CONTEXT('CTX_FUNCEF','UNIDADE_ID',p)
```

[!WARNING]

**Caveat de connection pool (.NET / FUNCEF.ORM)**

Como a conexão é reutilizada do pool, o contexto **deve ser setado no início de cada requisição/comando** e **limpo ao devolver** a conexão — senão uma requisição herda o contexto de outra. Padrão: um interceptor EF Core / `DbConnection` que chama `PKG_CTX_FUNCEF.set_*` logo após abrir a conexão, dentro da transação. Com RLS ativa, as queries do EF Core já vêm filtradas (transparente); **não** duplicar o filtro no LINQ para a mesma dimensão.

**Alternativa sem RLS:** quando a segregação é simples e 100% coberta/testada na camada de Service, filtrar na aplicação é aceitável (RLS adiciona complexidade operacional). RLS é para *defesa em profundidade* e casos onde o filtro não pode depender só do app.

8.4 Checklist específico

  • [ ] **Nenhum** uso de `BOOLEAN` em DDL.
  • [ ] Flags são `NUMBER(1) NOT NULL + CHECK IN (0,1)` (ADR-017; legado `CHAR(1) 'S'/'N'` permanece).
  • [ ] Nenhuma expressão derivada compara `FLAG_*` numérico a `'S'`/`'N'` (evita `ORA-01722`).
  • [ ] Nome das flags segue convenção `FLAG_`.
  • [ ] **Toda tabela nova** tem **`DATA_INCLUSAO_ALTERACAO DATE NOT NULL`** (ADR-016); omissão só com exceção justificada registrada.
  • [ ] Tabelas de domínio estáticas **não** têm a coluna (a não ser exceção justificada).
  • [ ] Coluna mantida pela aplicação (não por trigger, salvo exceção).
  • [ ] Tipos seguem o catálogo de [Stack-Canonica](../../backend/_shared/Stack-Canonica.md).
  • [ ] `VARCHAR2` declarado com `CHAR` (não `BYTE`).
  • [ ] Surrogate key `_ID NUMBER GENERATED BY DEFAULT AS IDENTITY NOT NULL`.
