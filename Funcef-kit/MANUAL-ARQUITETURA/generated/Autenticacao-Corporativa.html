Autenticação Corporativa e Operação (FrontEnd)

Nota **Papel**

Conhecimento operacional do frontend FUNCEF que complementa a arquitetura Feature-Based (FE-01..06): **autenticação corporativa**, **config de ambiente server-only** e **versionamento da lib (Changesets)**. Baseado no `web-template` v3.4.0.

Autenticação — `@funcef-componentes/auth` + Better Auth + Microsoft Entra

Auth, HTTP, shell e proxy vêm da **lib** — nada de cópia local de adapters. O template configura em `src/core/auth/`.

ItemValor / decisão
Lib de auth`@funcef-componentes/auth` **v3** (`^3.1.0`)
Better Auth`better-auth` **^1.6** (dependência direta; factory via auth lib)
Factory server`createFuncefAuth` em `src/core/auth/index.ts`
Sessão server`createGetServerSession(auth)` exportado do mesmo módulo
Client browser`createAuthClient` (better-auth/react) em `src/core/auth/client.ts` — baseURL `/api/auth`
Social provider**microsoft** (Entra ID): `clientId`, credencial (`clientSecret` \cert \federated), `tenantId`, `audience`
Storage de sessão`redisStorage` via `secondaryStorage` quando `REDIS_URL` presente; senão stateless com degradação graciosa
Credencial EntraCascata: `MICROSOFT_CLIENT_SECRET` → cert PEM → federated (`azureClientAssertion`)
Profile photo`profilePhoto: true` na factory (Graph + Redis quando disponível)
Cookies`cookieDomain` + `secureCookies` em produção; `COOKIE_MAX_AGE` opcional
Trusted origins`https://*.funcef.com.br` (configurável na factory)
Layout autenticado`getServerSession()` server-side → redirect se ausente; guard binário em `proxy.ts`
HTTP autenticado (BFF)Browser fala **só** com `/api/bff/*`; Bearer resolvido no `createBffHandler` — **nunca** no JS
Tratamento 401BFF devolve `401` → `createApi` sinaliza `AUTH_ERROR_EVENT` → teardown (`core/auth/teardown.ts`)

[!WARNING]

**Distinção dev × prod**

  • **dev:** sem `REDIS_URL` → sessão stateless/degradada. Cookies host-only.
  • **prod:** `REDIS_URL` recomendado; `COOKIE_DOMAIN` para cross-subdomain; `secureCookies: true`.

Guard de sessão — `src/proxy.ts`

import { createSessionProxy } from '@funcef-componentes/auth/proxy';

export const proxy = createSessionProxy({
  publicRoutes: ['/sign-in'],
  sessionCookieNames: [...DEFAULT_SESSION_COOKIE_NAMES],
  signInPath: '/sign-in',
  // ...
});
```
  • Guard **binário** (presença de cookie): anônimo em rota protegida → `/sign-in`; autenticado em rota pública → home.
  • **Não** é fronteira de segurança absoluta — a fronteira real é `getServerSession` no layout + backend a cada request + `401 → teardown`.
  • Cenário **Consumidor TKF2**: overlay via CLI (`pnpm dlx @funcef-componentes/cli scenario apply consumidor-tkf2`) — `signInPath` absoluto da porta de entrada.

BFF único — `app/api/bff/[...path]/route.ts`

import { createBffHandler } from '@funcef-componentes/auth/server';
import { auth } from '@/core/auth';

export const { GET, POST, PUT, PATCH, DELETE } = createBffHandler(auth, {
  upstreamUrl: env.API_URL,
  providerId: 'microsoft',
});
```
  • Um único BFF same-origin — não há `app/api//[...path]` por microsserviço no template base.
  • `API_URL` é **server-only** (`shared/config/env.ts`).

Configuração de ambiente — `env.ts` server-only

`src/shared/config/env.ts` valida via Zod no boot. Variáveis: `APP_URL`, **`API_URL`** (backend — **server-only**, usada só pelo BFF), `BASE_PATH`, `MICROSOFT_CLIENT_ID/SECRET` (ou cert/federated), `TENANT_ID`, `AUDIENCE_API`, `BETTER_AUTH_SECRET`, `REDIS_URL` (opcional em dev), `COOKIE_MAX_AGE`, `COOKIE_DOMAIN`, `NODE_ENV`.

[!CAUTION]

**`env.ts` vs `env-client.ts`**

  • `env.ts` usa `import 'server-only'` — só em código server (route handlers do BFF, Server Components, `getServerSession`, auth). **`API_URL` mora aqui** e nunca vaza para o cliente.
  • `env-client.ts` expõe apenas `NEXT_PUBLIC_*` (ex.: `APP_URL`, `BASE_PATH`) — pode ser importado de Client Components. **Não** colocar a URL do backend aqui.

Importar `env.ts` em código client **quebra o build propositalmente**. Não contornar.

Segurança web — CSP estática em `next.config.ts`

A superfície de segurança web do frontend está em **dois lugares canônicos**:

  1. **`src/proxy.ts`** — guard binário de sessão via `createSessionProxy` (sem CSP nonce por requisição).
  2. **`next.config.ts`** — headers estáticos + **CSP em produção** montada estaticamente:

- `script-src 'self' 'unsafe-inline' 'wasm-unsafe-eval'`

- `style-src 'self' 'unsafe-inline'`

- `connect-src 'self'` (backend via BFF same-origin — não entra aqui)

- `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`

- Também: `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, `Vary`

- CSP **só em produção** (`NODE_ENV === 'production'`); dev sem CSP para não quebrar HMR.

[!NOTE]

**WEB-1 — RESOLVIDO (BFF same-origin)**

O browser fala só com `/api/bff/*`; o Bearer é resolvido no servidor e nunca chega ao JS. Implementado via `createBffHandler` + `createApi`. Referência: `web-template/src/app/api/bff/[...path]/route.ts`, `src/core/api.ts`.

Versionamento da lib (Changesets)

A `lib-front-ui` usa **Changesets** — versionamento independente por pacote + changelog automático.

pnpm changeset            # descrever a mudança (escolher pacotes + bump semver)
# PR de versionamento é criado/atualizado automaticamente (version-publish.yml)
# ao merge, publica no GitHub Packages
```
  • CI/CD da lib: `ci-cd.yml` (lint + typecheck + build + test + deploy Storybook no GitHub Pages); `version-publish.yml` (Changesets → publish).
  • CI/CD do app: cada app define seu pipeline em `funcef-devops/`.
