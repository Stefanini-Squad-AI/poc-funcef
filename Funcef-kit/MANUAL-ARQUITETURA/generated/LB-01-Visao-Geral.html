LB-01 — Visão Geral: DB-as-Code com Liquibase

Nota **Mensagem-chave**

**A branch do ambiente é a porta de entrada para o banco.** Tratamos mudanças de banco como **código versionado, revisado e promovido por ambiente** — o banco deixa de ser "um lugar onde alguém roda script" e vira parte da esteira de entrega.

1.1 O cenário

Uma pessoa nova no time recebe uma demanda simples: *"criar uma tabela e uma package para uma nova funcionalidade"*. No modelo antigo, ela talvez aplicasse um script manualmente no banco. No modelo DB-as-Code, **tudo passa por Git, Pull Request, aprovação e Liquibase**. Este capítulo explica o porquê; os capítulos seguintes ensinam o caminho certo.

1.2 Por que abandonamos o modelo manual

Script manual parece rápido, mas gera **risco operacional**:

Modelo antigo (manual)Modelo novo (DB-as-Code)
Script aplicado manualmenteScript **versionado no Git**
Difícil saber quem aplicou e quando**Pull Request e aprovação** registram autoria/intenção
Risco de aplicar no ambiente errado**Execução automatizada por ambiente** (branch → ambiente)
Sem histórico confiável por ambienteHistórico no **Git** e no **`DATABASECHANGELOG`**
Correções feitas direto no bancoCorreção **sempre via novo changeset**

1.3 O que é DB-as-Code

flowchart LR
    G["Git<br/>scripts versionados"] --> P["Pull Request<br/>revisão e aprovação"]
    P --> L["Liquibase<br/>execução controlada"]
    L --> O["Oracle<br/>ambiente correto"]
```

Quatro responsabilidades distintas:

  • **Git registra a intenção** — o changeset versionado.
  • **PR aprova a mudança** — a barreira de controle humana.
  • **Promotion Policy valida o caminho** — impede promoção fora da cadeia.
  • **Liquibase aplica no banco** — após o merge na branch do ambiente.

[!IMPORTANT]

**Aprovação ≠ Execução**

**Aprovação = GitHub. Execução = Liquibase.** O *runner* não aprova nada; ele só executa **depois** do merge. Branch protegida significa que merge direto é bloqueado.

1.4 O que existe por trás do pipeline

ComponenteFunção
**GitHub**Repositório, branches, Pull Requests e regras (rulesets, CODEOWNERS)
**Liquibase**Lê os changelogs e aplica as mudanças no banco; mantém `DATABASECHANGELOG`
**Runner `runner-self-hosted-001`**Runner self-hosted que executa os jobs do GitHub Actions
**Podman**Sobe o container temporário da imagem `liquibase/liquibase` para rodar os comandos
**Oracle (DEV/HOM/PROD)**Ambientes de destino (no `nexus`: `ORCLPDB-DEV-001`; no `planus`: PDBs OCI/RAC)

Detalhes de cada um em [LB-07-Pipeline-CICD](../pipeline/LB-07-Pipeline-CICD.md).

1.5 Branches: o mapa dos ambientes

flowchart LR
    F["feature/* fix/* short/*"] --> DEV["dev<br/>Deploy DEV"]
    DEV --> HOM["hom<br/>Deploy HOM"]
    HOM --> MAIN["main<br/>Candidato PROD"]
```

**Regra de ouro:** o desenvolvedor trabalha em `feature/*`, `fix/*` ou `short/*` (tarefas rotineiras); merge em `dev`/`hom`/`main` **só via PR aprovado**. Detalhe do fluxo em [LB-05-Git-Pull-Request](../fluxo/LB-05-Git-Pull-Request.md).

1.6 Como o desenvolvedor trabalha no dia a dia

flowchart TD
    A[1. Criar branch feature/fix] --> B[2. Criar script DDL/DML/DCL/DQL/PLSQL]
    B --> C[3. Registrar include no changelog da categoria]
    C --> D[4. Commit e push da branch]
    D --> E[5. Abrir PR para dev]
    E --> F[6. Aguardar aprovação e merge]
    F --> G[Pipeline aplica automaticamente no banco DEV]
```

O ciclo é sempre o mesmo: **criar script → registrar include → commit → push → PR → aprovar → merge → deploy**. Promoção para HOM e MAIN repete o ciclo (PR `dev→hom`, depois `hom→main`).

1.7 Quem aprova antes de aplicar no banco

A aprovação acontece **no Pull Request, antes** do Liquibase rodar:

  • **PR para `dev`** — revisão técnica antes de aplicar em DEV.
  • **PR `dev → hom`** — aprovação após testes em DEV.
  • **PR `hom → main`** — aprovação final para baseline de produção.

Os aprovadores exigidos variam por **tipo de mudança** (DML/DDL/DCL/DQL/PLSQL) e **ambiente** — ver [LB-06-Governanca-Aprovacao](../governanca/LB-06-Governanca-Aprovacao.md) e [Matriz-Aprovacao](../_shared/Matriz-Aprovacao.md).

1.8 Relação com o PadraoBD (BD-NN) e com scripts manuais

flowchart TB
    subgraph QUE["O QUE escrever (conteúdo do SQL)"]
        BD[PadraoBD v2.2 — BD-01..10]
    end
    subgraph COMO["COMO entregar (este corpus)"]
        LB[DB-as-Code — LB-00..09]
    end
    BD -->|SQL do changeset segue o padrão| LB
```
  • **Conteúdo SQL** de cada changeset segue o **PadraoBD** ([BD-00-Orchestrator](../../BD-00-Orchestrator.md)): `TB_`/`VW_`, UPPERCASE, surrogate key, `FLAG_ NUMBER(1)+CHECK` (ADR-017), `COMMENT ON`, etc.
  • **Entrega** segue este corpus `LB-NN`.
  • **Hotfix emergencial** em PROD que (ainda) não passa pela esteira segue [Padroes-Scripts-Operacionais](../../operacional/Padroes-Scripts-Operacionais.md) (manual, defensivo, com DBA). A meta de longo prazo é trazer tudo para a esteira DB-as-Code — ver [LB-08-Correcao-Troubleshooting](../operacional/LB-08-Correcao-Troubleshooting.md) §8.7.
