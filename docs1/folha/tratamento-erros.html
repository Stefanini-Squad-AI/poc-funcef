O módulo FOLHA utiliza três padrões de tratamento de erros: (1) try/except com MessageDlg/ShowMessage para exibir mensagens ao usuário, (2) try/except com RollBack para reverter transações, e (3) raise exception.Create para propagar erros de validação. Foram contabilizados 1157 blocos try e 163 ocorrências de MessageDlg/ShowMessage/raise exception.Create nos arquivos .pas do módulo. O arquivo com mais blocos try é dFolhaPrevia.pas (233 blocos).

🔄 Padrões de Tratamento Identificados

try/except + RollBack

Usado em operações de escrita (prévia, efetivação, estorno). O except reverte a transação em dtmBaseDados.dbBaseDados e exibe MessageDlg. Padrão dominante em dFolhaPrevia.pas e fFolhaNormalEfet.pas.

try/except + MsgDlg

Usado em validações de rubrica, margem e IRRF. O except exibe MessageDlg com a mensagem de erro e aborta a operação do recebedor.

raise exception.Create

Usado para erros de log e falhas críticas: "Erro ao gravar Log." propagados para o chamador tratar.

try/finally (cleanup)

Usado em FPreparo, fImportaTxt e fFolhaNormalEfet para garantir liberação de queries/forms (Free) mesmo em caso de exceção.

try/except silenciado

Em algumas rotinas utilitárias o except é vazio ou apenas loga. PENDENTE — verificar se intencional.

📖 Para o leigo — Como o sistema lida com problemas (enriquecido — PFC-42)

Esta aba mostra como o módulo FOLHA reage quando algo dá errado. Pense num motorista de ônibus: se aparece um buraco na rua, ele pode desviar (mostrar uma mensagem e seguir), pode voltar para a garagem (desfazer a operação) ou pode ligar para a central (propagar o erro para alguém resolver). O sistema faz o mesmo.

Os três comportamentos principais quando há um erro:

  • Mostrar mensagem e seguir (try/except + MessageDlg) — o sistema exibe uma janela avisando o usuário ("Margem de desconto excedida") e interrompe aquela operação, mas o programa continua rodando. É o caso mais comum.
  • Desfazer a operação (try/except + RollBack) — quando o erro acontece no meio de uma gravação no banco, o sistema reverte tudo o que já tinha feito (rollback) para não deixar os dados pela metade, e avisa o usuário. É usado nas operações de prévia, efetivação e estorno.
  • Propagar o erro (raise exception.Create) — o sistema "joga" o erro para cima, para quem chamou a rotina tratar. Usado em erros críticos, como falha ao gravar log.

Quantidade: o módulo tem 1.157 blocos de tratamento de erro (try) e 163 mensagens de validação/erro. O arquivo com mais tratamentos é o motor de cálculo dFolhaPrevia.pas (233 blocos) — o que faz sentido, pois é onde mais coisas podem dar errado (cálculo de rubrica, margem, IRRF, gravação etc.).

Alguns erros têm o except vazio (silenciado) — o sistema captura o erro mas não faz nada. Isso pode ser intencional (o erro é esperado e irrelevante) ou pode ser um bug escondido. Estão marcados como PENDENTE para verificação.

💼 Para o analista de negócios — Pontos de falha de negócio (enriquecido — PFC-42)

Mensagens que indicam impacto de negócio direto (o usuário final as vê e precisa agir):

  • "Margem de desconto excedida" (dFolhaPrevia.pas:7496) — um desconto consignado foi bloqueado. Ação: verificar se a margem do beneficiário está correta ou se o desconto deve ser renegotiado.
  • "Valor líquido negativo — desconto transferido" (FOLHA-RN006) — o beneficiário receberia valor negativo; o sistema zerou e transferiu o desconto. Ação: revisar rubricas de desconto daquele beneficiário.
  • "Lote já efetivado" (fFolhaNormalEfet.pas) — tentativa de efetivar uma folha já paga. Ação: usar o estorno (PF-04) se necessário, ou escolher outra competência.
  • "Prévia não encontrada para o período" (FFolhaNormalPrevia.pas) — tentativa de efetivar sem prévia calculada. Ação: calcular a prévia primeiro.
  • "Falha na geração do CNAB" (fFolhaNormalEfet.pas:9346) — o arquivo bancário não foi gerado. Ação: verificar configuração de leiaute e permissões de pasta; sem o arquivo, o banco não paga.

Risco do try/except silenciado: erros capturados e ignorados podem mascarar problemas reais (ex.: falha de gravação que o usuário não percebe). Para o analista, isso significa que algumas falhas podem estar ocorrendo sem reportar — recomenda-se auditar os except vazios, especialmente no motor de cálculo e na efetivação.

Resiliência operacional: o padrão dominante (try/except + RollBack) garante que o banco não fique inconsistente em caso de erro. No entanto, uma folha interrompida no meio pode deixar a competência em estado parcial — o estorno existe para corrigir. Recomenda-se sempre verificar o estado da competência após uma falha antes de prosseguir.
