🏗️ Arquitetura do Módulo

O módulo BENEFICIOPREV tem 144 artefatos. O entry point BeneficioPrev.dpr cria o splash CM e o form principal frmPrincipal (Caption "Concessão e Manut de Benefícios Previdenciários", IdModulo SAD=454). O menu de Eventos é montado dinamicamente em runtime lendo EVENTOGERADOR por FLGINTERNO (TS/ID/IN/FL/AI/BI/RC/DO/OE).

A arquitetura segue o padrão CM com SQL inline dominante via TwwQuery/TQuery. A camada CtrlObjects/+DBObjects/ cobre apenas 2 entidades locais (EVOLFUNCPREV, HISTRUBSAL); o motor de cálculo/concessão reside no pacote externo CMAdmPrev — o BENEFICIOPREV atua principalmente como orquestrador de UI, eventos, manutenção, conciliação INSS e desfazimento.

Toda operação de negócio é auditada em LOGTOTALPREV (IdModulo=454). Filtros de multi-fundação (IDFUNDACAO/PATRO) estão presentes em quase toda SQL de negócio.

Nota (PENDENTE): O uses do DPR referencia unidades sem prefixo (FConciliacao, FIdentificaINSS, etc.) mas no filesystem existem versões com underscore (_FConciliacao.pas, ...). O DPR está parcialmente dessincronizado do diretório; a compilação real provavelmente usa os arquivos _ (alternativos/mais novos).

Evidência: ~92% COMPROVADO, ~6% INFERIDO, ~2% PENDENTE.

📖 Para o leigo — Como o programa é organizado (enriquecido — PFC-42)

Este módulo é como uma repartição pública de benefícios com vários departamentos. A arquitetura descreve como esses departamentos se organizam.

As quatro camadas (do mais visível ao mais interno):

  • Telas (Apresentação) — 68 janelas que o usuário vê: concessão, manutenção, simulação, eventos (aposentadoria, falecimento, reclusão), reajuste, desdobramento, conciliação INSS, desfazimento.
  • Controle — 2 objetos de controle (evolução funcional e listas PCS). Camada fina neste módulo.
  • Acesso a Dados — 2 objetos de banco locais (EVOLFUNCPREV, HISTRUBSAL) + muito SQL embutido" nos forms + DataModules externos (CMAdmPrev, CMPrevMT50).
  • Framework base — o CM Framework (20+ units) + CMAdmPrev (8 units) fornecem telas padrão, autorização, consultas e relatórios.

Uma característica importante: o motor de cálculo/concessão reside no pacote externo CMAdmPrev. O BENEFICIOPREV atua principalmente como orquestrador de UI (telas), eventos, manutenção, conciliação INSS e desfazimento. A inteligência de cálculo fica em outro módulo.

Menu dinâmico de eventos — o menu de Eventos (aposentadoria, falecimento, reclusão etc.) é montado em runtime lendo a tabela EVENTOGERADOR por FLGINTERNO (TS=Tempo de Serviço, ID=Idade, IN=Incapacidade, FL=Falecimento, AI/BI=INSS, RC=Reclusão). Alguns eventos (DO=Doença, AC=Acidente, OE=Outros) estão comentados no código — inativos.

Auditoria: toda operação de negócio é registrada em LOGTOTALPREV (IdModulo=454), com data, usuário e descrição da operação.

💼 Para o analista de negócios — Impacto e risco de mudança (enriquecido — PFC-42)

Separação de responsabilidades: o BENEFICIOPREV é "mostly UI" — a lógica de cálculo/concessão está no CMAdmPrev. Isso significa que mudanças na regra de cálculo (valor do benefício, elegibilidade) devem ser feitas no CMAdmPrev, não aqui. O BENEFICIOPREV cuida do fluxo de telas, validações de entrada e orquestração.

Dependência crítica do CMAdmPrev (8 units, 40 refs a UAdmPrev): sem o CMAdmPrev, não é possível conceder, manter ou simular benefícios. É a dependência mais crítica do módulo.

DPR dessincronizado (risco técnico): o uses do projeto referencia units sem prefixo (FConciliacao, FIdentificaINSS) mas no filesystem existem versões com underscore (_FConciliacao.pas). A compilação real provavelmente usa os arquivos _. Impacto: risco de compilar contra versões erradas; recomenda-se alinhar o DPR com o filesystem.

Eventos inativos (DO/AC/RC/OE) — Doença, Acidente, Reclusão e Outros Eventos estão comentados no código. Impacto de negócio: esses eventos não podem ser registrados via menu. Se houver demanda de negócio para eles, precisam ser reativados.

Filtros de multi-fundação (IDFUNDACAO/PATRO) presentes em quase toda SQL de negócio. Isso significa que o módulo suporta múltiplas fundações/institutos no mesmo banco — relevante para decisões de shared infrastructure.
