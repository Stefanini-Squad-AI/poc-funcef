🏗️ Arquitetura do Módulo

O módulo CONTRIBUIÇÃO (pasta CONTRIBUICAOPREV) tem 158 artefatos. O entry point ContribuicaoPREV.dpr cria o splash CM, auto-instancia DataModules (dtmAPrev, dtmIntegraCAPCAR, dtmAPrevIntegraBack, dtmPreparaContrib, dmRetroativoLote) e o form principal frmPrincipal (Caption "Manutenção e Cobrança de Contribuição").

A arquitetura é híbrida: herança CM framework + DataModules InfoPower (TwwQuery) com SQL inline massivo nos forms (baixa separação de camadas). A camada CtrlObjects/+DBObjects/ existe mas cobre apenas 2 entidades locais (EVOLFUNCPREV, HISTRUBSAL); o restante do acesso a dados é direto nos forms ou via DataModules externos de CMAdmPrev e CMPrevMT50.

Os CtrlObjects operam em modo dual: cnsClient delega ao Connection.AppServer (AppServer remoto CM); caso contrário executa SQL local. Integração OLE/Excel é usada para alteração em lote de salários. Package Oracle PCK_BENEFSALDFAB.SP_ATUALIZASALDO é invocado para benefício saldado/FAB.

Evidência: COMPROVADO — DPR, DBObjects, CtrlObjects e SQL inline verificados.

📖 Para o leigo — Como o programa é organizado (enriquecido — PFC-42)

Este módulo é como uma empresa de cobrança com vários departamentos. A arquitetura descreve como esses departamentos se organizam.

As quatro camadas (do mais visível ao mais interno):

  • Telas (Apresentação) — 75 janelas que o usuário vê: envio de cobrança, recebimento, alimentação de reservas, provisão para perdas etc.
  • Controle — 2 objetos de controle (evolução funcional e listas PCS). Camada fina neste módulo.
  • Acesso a Dados — 2 objetos de banco locais (EVOLFUNCPREV, HISTRUBSAL) + muito SQL embutido" diretamente nos forms + DataModules externos (CMAdmPrev, CMPrevMT50).
  • Framework base — o CM Framework (27 units) + CMAdmPrev (11 units) fornecem telas padrão, autorização, consultas e relatórios.

Uma característica importante: a arquitetura é híbrida. Embora exista a camada de controle/acesso a dados, ela cobre apenas 2 entidades locais. O restante do acesso a dados é feito direto nos forms, com SQL embutido" (inline). Isso significa que a separação de responsabilidades é menor que no módulo FOLHA — a lógica de negócio e o acesso a dados estão mais misturados.

Integração com Excel é usada para alteração em lote de salários de participação (OLE/ADO). E procedures Oracle (PCK_BENEFSALDFAB.SP_ATUALIZASALDO) são invocadas para benefício saldado/FAB.

💼 Para o analista de negócios — Impacto e risco de mudança (enriquecido — PFC-42)

Dívida técnica: a arquitetura híbrida com SQL inline nos forms torna a manutenção mais difícil e arriscada. Uma mudança de regra pode exigir editar SQL em vários forms, sem a centralização que um ORM proporcionaria. Impacto: maior esforço de manutenção e maior risco de inconsistência entre telas.

Dependência massiva de CMPrevMT50 (1.395 referências a; DPLANOPREV): o módulo depende fortemente de DataModules externos para acessar entidades previdenciárias centrais. Uma mudança no CMPrevMT50 pode afetar o CONTRIBUIÇÃO em dezenas de pontos.

Modo dual cliente/servidor: os CtrlObjects operam em dois modos — cnsClient (delegação para AppServer remoto CM) ou SQL local. Isso significa que o módulo pode rodar tanto em arquitetura cliente-servidor quanto em 3 camadas (MIDAS/DataSnap). Para o analista, isso é relevante para decisões de infraestrutura e migração.

Procedures Oracle críticas: SP_CP_RECEB_PATRO/ASSIS (recebimento via folha) e PCK_BENEFSALDFAB (benefício saldado/FAB). Essas procedures são pontos de acoplamento com o banco — mudanças no Oracle podem afetar o comportamento sem que o código Delphi seja alterado. Recomenda-se versionar e testar as procedures junto com o código Delphi.

Integração Excel (OLE/ADO): a alteração em lote de salários via planilha é um ponto de risco — erros de importação (células vazias, formatos incorretos) podem gerar salários errados e, consequentemente, contribuições erradas. O hash CRC32 é usado para controle, mas a validação de conteúdo deve ser rigorosa.
