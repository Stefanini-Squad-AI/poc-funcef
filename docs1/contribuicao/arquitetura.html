💡 Em linguagem simples (enriquecido — PFC-42)

O que esta aba mostra: como o módulo é “montado por dentro”: quais peças existem, onde ficam e como conversam entre si. Uma boa analogia é um restaurante: as telas são o salão (onde o cliente faz o pedido), o código das telas é a cozinha (onde as regras são aplicadas), o banco Oracle é a despensa (onde tudo fica guardado) e os outros módulos (Folha, Financeiro, Contabilidade) são fornecedores e parceiros.

Por que isso importa: saber onde a regra “mora” ajuda a estimar o esforço de qualquer mudança. Neste módulo, a maior parte das regras está escrita dentro das próprias telas, junto com os comandos SQL — por isso uma mudança de regra quase sempre exige mexer na tela correspondente.

Como ler esta página: a tabela “Camadas e Componentes” mostra os andares do prédio; “Dependências Internas” mostra quem chama quem; o inventário por área agrupa as telas por assunto de negócio. Os blocos “💡 Em outras palavras” traduzem cada parte.

💡 Em outras palavras: o módulo tem três “andares”: telas (o que o usuário vê), controle (poucas peças que coordenam regras) e acesso a dados. Na prática, porém, as telas fazem quase tudo: o preparo de contribuições, por exemplo, está inteiro em FPreparaEnvia.pas, com 7.261 linhas, incluindo os comandos SQL COMPROVADO. As telas acessam o banco diretamente pelo alias “BaseDados” (FCalcSalContr.pas:458-468) COMPROVADO, o que indica um modelo cliente-servidor em que o programa do usuário fala direto com o Oracle INFERIDO.

👔 Para o analista de negócios

  • Regra dentro da tela = mudança mais cara. Como a lógica de negócio está misturada com a interface, alterar uma regra (ex.: cálculo de contribuição) exige testar a tela inteira. Considere isso ao priorizar ou estimar demandas.
  • Parte das regras está no banco. O recebimento via folha usado no menu chama procedimentos guardados no Oracle (CM.SP_CP_RECEB_PATRO / CM.SP_CP_RECEB_ASSIS) (FRecebeContribuicaoNovo.pas:925, 954) COMPROVADO, e o benefício saldado usa o pacote CM.PCK_BENEFSALDFAB (FBeneficioSaldadoFAB.pas:1032) COMPROVADO. Para validar essas regras é preciso olhar também o banco, não só as telas.
🏗️ Arquitetura do Módulo

O módulo CONTRIBUIÇÃO (pasta CONTRIBUICAOPREV) tem 158 artefatos. O entry point ContribuicaoPREV.dpr cria o splash CM, auto-instancia DataModules (dtmAPrev, dtmIntegraCAPCAR, dtmAPrevIntegraBack, dtmPreparaContrib, dmRetroativoLote) e o form principal frmPrincipal (Caption "Manutenção e Cobrança de Contribuição").

A arquitetura é híbrida: herança CM framework + DataModules InfoPower (TwwQuery) com SQL inline massivo nos forms (baixa separação de camadas). A camada CtrlObjects/+DBObjects/ existe mas cobre apenas 2 entidades locais (EVOLFUNCPREV, HISTRUBSAL); o restante do acesso a dados é direto nos forms ou via DataModules externos de CMAdmPrev e CMPrevMT50.

Os CtrlObjects operam em modo dual: cnsClient delega ao Connection.AppServer (AppServer remoto CM); caso contrário executa SQL local. Integração OLE/Excel é usada para alteração em lote de salários. Package Oracle PCK_BENEFSALDFAB.SP_ATUALIZASALDO é invocado para benefício saldado/FAB.

Evidência: COMPROVADO — DPR, DBObjects, CtrlObjects e SQL inline verificados.

💡 Em outras palavras: ao abrir o programa, o arquivo de partida já cria, de uma vez, as “caixas de ferramentas” de dados (dtmAPrev, dtmIntegraCAPCAR, dtmAPrevIntegraBack, dtmPreparaContrib, dmRetroativoLote) e a tela principal — e também várias outras peças auxiliares e de relatório (ContribuicaoPREV.dpr:154-175) COMPROVADO. É como ligar todas as máquinas da cozinha antes de o primeiro cliente chegar.

👔 Para o analista de negócios — síntese (PFC-42)

Em termos de negócio, a arquitetura do CONTRIBUIÇÃO tem três consequências práticas:

  • Conhecimento concentrado em poucas telas grandes: FDivergContrib (9.694 linhas), FRecebeContribuicao (7.803), FPreparaEnvia (7.261) e FControleIndivContrib (5.800) concentram as regras mais críticas COMPROVADO. São os pontos onde vale investir em documentação e testes.
  • Regras divididas entre tela e banco: o recebimento via folha ativo usa procedimentos Oracle (FRecebeContribuicaoNovo.pas:925-967) COMPROVADO; o código-fonte de CM.Sp_Cp_Receb_Patro está no repositório, em SCRIPT/SIG33372/04_Script_SIG33372_DDL (Sp_Cp_Receb_Patro).txt COMPROVADO.
  • Dependência de outros módulos para compilar: relatórios gerenciais vêm de pastas de outros módulos (ver ponto a validar acima). Uma mudança nesses módulos pode afetar o CONTRIBUIÇÃO sem que ninguém perceba.

Perguntas para levar ao responsável de negócio:

  1. Existe ambiente de testes onde uma alteração de regra no preparo ou no recebimento possa ser validada com dados reais anonimizados?
  2. A versão dos procedimentos Oracle em produção é a mesma guardada em SCRIPT/SIG33372?
  3. A tela legada de recebimento via folha (fora do projeto) ainda é usada em algum outro executável?
