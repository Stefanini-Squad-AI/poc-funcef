O que esta aba mostra: como o módulo reage quando algo dá errado: dados faltando, valor inválido, falha no banco de dados ou numa integração. Mostra os “padrões de reação” do código e as mensagens mais importantes que o usuário pode ver.

Por que isso importa: um erro mal tratado pode deixar dados pela metade (parte gravada, parte não) ou passar despercebido. Para o negócio, isso significa contribuições com status errado, cobranças em duplicidade ou lacunas na trilha de auditoria.

⚠️ Visão Geral

O módulo CONTRIBUIÇÃO utiliza três padrões de tratamento de erros: (1) try/except com MessageDlg/ShowMessage, (2) try/except com RollBack para reverter transações, e (3) raise exception.Create para propagar erros. Foram contabilizados 346 blocos try e 53 ocorrências de MessageDlg/ShowMessage/raise exception.Create. O arquivo com mais blocos try é FDivergContrib.pas (56 blocos).

💡 Em outras palavras: o código usa três reações principais a erros: avisar o usuário, desfazer o que estava sendo gravado (rollback) ou disparar um alarme para a rotina que chamou. O ideal é que toda operação que grava dados tenha as duas primeiras juntas.

🔎 Ponto a validar PENDENTE — o total de “53 ocorrências de MessageDlg/ShowMessage/raise” não inclui MsgDlg, o comando de mensagem do framework CM usado 622 vezes no módulo (ver tabela acima). A contagem de “346 blocos try” também difere de uma contagem de linhas que começam com try (462). É preciso padronizar o critério.

👔 Para o analista de negócios

  • Mensagens são um bom insumo para manuais e treinamento: cada uma indica uma regra (ex.: “Preencha pelo menos uma patrocinadora para esta operação.”, FAtualizaPorIndice.pas:294) COMPROVADO.
  • Alguns avisos de erro oferecem botão de ajuda (mbHelp), por exemplo “Operação Interrompida com Erros.” (FAtualizaPorIndice.pas:518) COMPROVADO. Verifique se o conteúdo de ajuda existe e está atualizado.
  • Telas de importação controlam acesso com a mensagem “Você não tem permissão para acessar esta tela.” (FAlteraHistMovReserva.pas:471) COMPROVADO.
🔄 Padrões de Tratamento Identificados

try/except + RollBack

Usado em operações de escrita (preparo, envio, recebimento, divergências). O except reverte a transação e exibe MessageDlg. Padrão dominante em FPreparaEnvia.pas e FRecebeContribuicao.pas.

try/except + MsgDlg

Usado em validações de situação, valor e divergência. O except exibe MessageDlg e aborta. Padrão dominante em FDivergContrib.pas.

raise exception.Create

Usado para erros de log: "Erro ao gravar Log." em FDivergContrib.pas:5019 e outros.

try/finally (cleanup)

Usado em FPrincipal (login, CriaDataModule) para garantir liberação de recursos (Free de forms/queries).

💡 Em outras palavras: os cartões resumem as “receitas” de tratamento de erro. O padrão mais seguro é o “try/except + RollBack”: se algo falha, tudo o que foi feito naquela operação é desfeito, evitando dados pela metade.

🔎 Ponto a validar PENDENTE — o cartão “raise exception.Create” diz que “Erro ao gravar Log.” é propagado ao chamador. Em pelo menos um caso o alarme é disparado dentro de um try … except end vazio e, portanto, é descartado: FAtualizaPorIndice.pas:929-933. O mesmo padrão aparece nas telas citadas na lacuna TRT053/MSG100 do UC208 (aba 🔍 Lacunas). Confirmar se a falha de log deve bloquear a operação.

🔎 Ponto a validar PENDENTE — no envio de e-mail de “Contribuições não recolhidas”, o código marca o e-mail como enviado dentro do bloco de erro, com o comentário “quando envia o e-mail sem erros, cai nesse exception” (FDivergContrib.pas:9146-9147). Ou seja, o sucesso é detectado por uma exceção — se houver uma falha real, ela também pode ser registrada como “enviado”.

👔 Para o analista de negócios — síntese (PFC-42)

Do ponto de vista de negócio, o tratamento de erros do CONTRIBUIÇÃO tem três riscos principais:

  • Erros silenciosos: 64 blocos de erro vazios podem esconder falhas — inclusive na gravação do log de auditoria COMPROVADO.
  • Gravação parcial: o preparo e o envio salvam em blocos de 800 registros (FPreparaEnvia.pas:4174-4180, 5456) COMPROVADO; um erro no meio não desfaz os blocos já salvos.
  • Sucesso “por exceção”: o envio de e-mail considera sucesso o caminho de erro (FDivergContrib.pas:9146-9147) COMPROVADO.
  • Mensagens como regras: o texto das mensagens é uma boa fonte para confirmar regras de negócio com os usuários.

Perguntas para levar ao responsável de negócio:

  1. Falhas na gravação do log de operações devem impedir a conclusão da operação?
  2. Há procedimento definido para identificar e corrigir um preparo ou envio que parou no meio?
  3. Como a área confirma hoje que os e-mails de contribuições não recolhidas foram realmente entregues?
