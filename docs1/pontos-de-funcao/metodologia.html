💡 Entenda esta página

O que esta página mostra: as regras usadas para contar Pontos de Função. Explica o que cada tipo de função mede, como a complexidade é determinada e como os valores foram calculados. Serve para que qualquer analista possa revisar ou reproduzir a análise.

Por que isso importa: a Análise de Pontos de Função (APF) é um método padronizado de medir o tamanho funcional de software. Sem metodologia explícita, os números não são auditáveis. Esta página torna a contagem rastreável e reproduzível.

📐 O que a APF IFPUG mede

A Análise de Pontos de Função (APF) pelo método IFPUG FPA (International Function Point Users Group — Function Point Analysis) mede o tamanho funcional de um software sob a perspectiva do usuário. A unidade de medida é o Ponto de Função (PF). O método:

  • Mede o que o sistema faz (funcionalidade), não como foi implementado (tecnologia, linhas de código, componentes).
  • É independente de tecnologia: o mesmo conjunto de funções tem o mesmo número de PF, seja em Delphi 5, .NET, Java ou qualquer outra linguagem.
  • É baseado na fronteira da aplicação: o que está dentro da fronteira é contado; o que está fora é referenciado.
  • Fornece uma base auditável: cada função contada tem tipo, complexidade e fonte documentados.

Versão do método: IFPUG FPA, conforme as regras de contagem funcionais estabelecidas pelo IFPUG. Os conceitos e tabelas de complexidade usados nesta análise seguem o padrão IFPUG (DET/FTR/RET, tabelas de complexidade para funções de dados e transacionais). Não é alegada conformidade com uma versão específica do manual sem acesso às regras necessárias; a metodologia aplicada é a prática padrão de IFPUG FPA amplamente documentada.

🏷️ Os cinco tipos de função

A APF classifica as funções do sistema em dois grupos e cinco tipos:

GrupoTipoSiglaO que mede
Funções de dados
(o que o sistema guarda)		Arquivo Lógico InternoILFGrupo de dados logicamente relacionado, mantido (criado, atualizado ou excluído) dentro da fronteira da aplicação. Reconhecido pelo usuário.
Arquivo de Interface ExternaEIFGrupo de dados logicamente relacionado, mantido por outra aplicação e apenas lido pela aplicação em análise. Reconhecido pelo usuário.
Funções transacionais
(o que o sistema faz)		Entrada ExternaEIProcesso que envia dados ou controle para dentro da fronteira, mantendo um ou mais ILFs. O objetivo principal é manter dados.
Saída ExternaEOProcesso que envia dados ou controle para fora da fronteira. O objetivo principal é apresentar informações com dados derivados/calculados ou manter dados como efeito secundário.
Consulta ExternaEQProcesso que envia dados ou controle para fora da fronteira com dados não derivados (apenas recuperação de informações sem cálculo).

Cada função recebe um peso em PF conforme sua complexidade (Baixa, Média, Alta). A soma de todos os pesos é o total de Pontos de Função Não Ajustados (UFP).

🛡️ Delphi 5 como contexto técnico, não fator de pontuação

O sistema foi desenvolvido em Delphi 5 (VCL, Oracle, MIDAS/DataSnap, suíte CM Contabilidade / FUNCEF). Na APF IFPUG:

  • Delphi 5 é registrado como característica técnica do sistema, não como fator de classificação ou pontuação.
  • Não foram convertidas linhas de código, formulários (.dfm), units (.pas), componentes, classes, procedures, métodos ou eventos Delphi em Pontos de Função.
  • Não foram contadas telas, formulários ou componentes por existência técnica — apenas funções lógicas reconhecidas pelo usuário.
  • O código-fonte Delphi 5 foi usado como evidência auxiliar para es>clarecer comportamento, persistência e integrações — não como substituto dos requisitos funcionais.

Informação técnica complementar: métricas técnicas (linhas de código, inventário de componentes) ficam em seção separada na documentação do Blueprint e não são somadas nem convertidas em Pontos de Função. Ver Linhas de Código a Migrar no portal do Blueprint.

🔀 Integrações e dupla contagem

Uma integração ou chamada entre módulos não gera Pontos de Função automaticamente. A interação só é contada se for uma função reconhecível pelo usuário dentro da fronteira e atender às regras do método.

📖 Exemplo didático de contagem

Exemplo baseado em uma função documentada do módulo FOLHA: "Calcular a prévia da folha" (UC101 / JF002).

Função: EI-02 — Calcular prévia da folha (UC101 / JF002)

Tipo: EI (Entrada Externa) — o usuário seleciona patrocinadoras, planos e competência; o sistema processa e mantém os ILFs PREVIA, BASEDEPAGAMENTO e BITRIBUTACAO.

Fonte: UC101 — JF002 (Prévia / Cálculo da Folha); motor dFolhaPrevia.pas (30.856 linhas).

FTR (arquivos referenciados): 5 — PREVIA (mantido), PROVDESC (lido), BENEFBFCIARIO (lido), BASEDEPAGAMENTO (mantido), BITRIBUTACAO (mantido).

DET (elementos de dados): 30+ — mês/ano de referência, patrocinadora, plano, beneficiário, rubrica, valor provento, valor recebido, flags de cálculo (FLGIRRF, FLGDESCONTO, FLGMARGEMCONSIG...), valor líquido, base de IR, margem consignável, etc. COMPROVADO pelos 57 campos de PREVIA (docs1/folha/dados.html).

Classificação de complexidade:

  • FTR = 5 → faixa "3+"
  • DET = 30 → faixa "16+"
  • Interseção na tabela EI: FTR 3+ × DET 16+ = Alta

Peso: EI de complexidade Alta = 6 PF.

Justificativa: o cálculo da prévia é o processo central do módulo FOLHA. Ele lê múltiplos arquivos de configuração (rubricas, benefícios) e mantém vários arquivos de saída (prévia, bases de pagamento, bitributação). O alto número de DETs reflete os 57 campos documentados de PREVIA e os parâmetros de cálculo. A complexidade Alta é consistente com o volume do motor de cálculo (30.856 linhas em dFolhaPrevia.pas).

✅ Critérios aplicados nesta contagem
  • Funções de dados: cada tabela com DBObject (uDb*.pas) ou escrita por SQL inline com evidência de INSERT/UPDATE/DELETE foi avaliada como ILF (se mantida dentro da fronteira) ou EIF (se mantida por outra aplicação e apenas lida).
  • Funções transacionais: cada caso de uso (UC) documentado em docs1/ foi mapeado para uma ou mais funções EI/EO/EQ, conforme o objetivo principal do processo (manter dados = EI; apresentar dados derivados = EO; recuperar dados sem cálculo = EQ).
  • DET: contado a partir dos campos documentados nas páginas de dados (dados.html) de cada módulo. Onde o número exato de campos não foi extraído do código, o DET é estimado e marcado PENDENTE para confirmação.
  • RET: inferido a partir da chave primária documentada (chaves compostas sugerem múltiplos RETs) e da presença de tabelas detalhe associadas.
  • FTR: contado a partir dos ILFs/EIFs referenciados em cada processo, conforme documentado nas páginas de funcionalidades e dados.
  • Não contados: mensagens, logs, dados derivados, telas, formulários, units, components, procedures, métodos, eventos ou linhas de código. Não contada a mesma capacidade por aparecer em mais de uma jornada ou tela.
  • Pendências: funções cujos DETs/FTRs/RETs não puderam ser determinados com evidência são marcadas PENDENTE e não apresentadas como contagem confirmada.
👔 Para o analista de métricas
  • Revisão: cada função contada tem tipo, complexidade, peso e fonte documentados na página do módulo. Para revisar, abra a página do módulo, vá à seção "Inventário" e confira a "Memória de cálculo".
  • Reprodução: o total de PF de cada módulo é recalculado somando os pesos do inventário. Qualquer divergência entre o inventário e o sumário indica erro de totalização.
  • Validação recomendada: confirmar com especialistas de negócio (1) as fronteiras entre os três módulos, (2) o "dono" funcional de BENEFBFCIARIO e PROCESSOBENEF (dupla contagem), (3) os DETs marcados PENDENTE.
  • Contagem confirmada vs. preliminar: funções com evidência completa são contagem confirmada. Funções com DET/RET/FTR estimado são preliminares e estão na seção "Pendências de validação" de cada módulo.
